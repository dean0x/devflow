# Decisions Delivery and Curation Variants

## Rules

- **KB-INV-1** Decisions reach an agent on one route: the main model reads `{ledger}/.devflow/curation/index.md` and hands a slice of it on as `DECISIONS_CONTEXT`; nothing parses the ledger, and an agent reads the full index only at the path a slice names, when its work leaves the slice.
- **KB-INV-2** `DECISIONS_CONTEXT` goes only to an agent type whose source lists it among its inputs; `tests/decisions/decisions-seam.test.ts` computes that set from the agent sources, and every spawn site of a Code variant (Code, Fix, Refactor) carries the key.
- **KB-INV-3** All decisions text in commands and agents sits inside curation-on arms (`<!-- curation:on -->`), which the build resolves into two variants of each prompt; arms never nest and a marker is a whole line, removed whole.
- **KB-INV-4** `decisions_gate()` sets `DECISIONS_CONTEXT` to `(none)` and skips the step when the settings line says `CURATION=off`, before it locates a ledger or reads an index; an unresolvable settings line reads `CURATION=off`, as does the line of a project where git tracks the curation data folders or does not answer for them.
- **KB-INV-5** The install and the toggle follow the MACHINE switch alone; a repository's narrowing changes no installed file, which is why the curation-on variants keep the run-time `CURATION` gate.
- **KB-INV-6** The converge touches only installed files, writes byte-compared and atomically, isolates each item, and only warns on a skip or failure, never changing the exit code.
- **KB-INV-7** The converge carries an installed agent's `model:` and `effort:` and `/code-review`'s language-focus stamp into the variant before comparing, so `devflow agents` and proxy overrides survive and a no-op converge writes no agent.
- **KB-INV-8** The pass rule (`DECISIONS_PASS_RULE`) lives in the session-start decisions block, emitted only with an Index line, and names the slice (`tests/shell-hooks.test.ts` pins the literal); the orchestrator charter holds no decisions text.
- **KB-INV-9** `CURATION_VARIANT_HOSTS` in `tests/fixtures/mds-manifest.ts` names every host that carries an arm; the build's printed variant count, the files under `dist/curation-off` and the packed tarball are all asserted against it.
- **KB-INV-10** `CURATION_GATED_SKILLS` (`apply-decisions`) is left out of a curation-off install but stays owned and required by its plugins in the registry, so a curation-off machine never reports it as a deselection.
- **KB-INV-11** A curation-off agent file carries no apply-decisions preload (the variant is the mechanism, with no install-time frontmatter rewrite), and a curation-on file keeps the preload plus the run-time gate.
- **KB-INV-12** The Code agents' `DECISIONS_CONTEXT` input bullet and apply-decisions step are written once, in the shared partial `src/assets/agents/_partials/_code.mds` (`input_core()` and `decisions_orient()`, each in a curation-on arm); the `code`, `fix` and `refactor` hosts call them and keep only their own preload arm.
- **KB-INV-13** The index is handed on as a slice, never whole: the main model copies the index lines that touch an agent's work, verbatim, behind a `(slice: N of M entries — full index: <path>)` marker and ahead of the footer; siblings over one diff share ONE slice, and when unsure it includes the line. `tests/decisions/decisions-slice.test.ts` holds it.
- **KB-INV-14** No script cuts the slice, and `decisions_slice()` is a leaf with no arm of its own, expanded only inside curation-on arms, so a curation-off build carries none of the rule.
- **KB-AP-1** Decisions text outside a curation-on arm (a `DECISIONS_CONTEXT` input bullet, an apply-decisions step or preload, a `decisions_load()` expansion, a pass site): it reaches curation-off machines, which are meant to carry none of it.
- **KB-AP-2** Handing `DECISIONS_CONTEXT` to an undeclared agent type, or to "all subsequent agents": the index is the largest single input a command can give an agent, so name the declared receivers.
- **KB-AP-3** Giving Code an index read of its own, or the apply-decisions Skip Guard a clause for one: a Code spawn without the key has no decisions.
- **KB-AP-4** Stating the pass rule in the orchestrator charter: the charter is paid in every session, curation or not.
- **KB-AP-5** Rewriting an installed agent's frontmatter to drop the preload on a toggle, or deciding the preload from a repository's narrowing: the installed agents are machine-wide.
- **KB-AP-6** Leaving a blank line outside the arm that owns its paragraph: it doubles in the other variant.
- **KB-AP-7** Adding or removing an arm without updating `CURATION_VARIANT_HOSTS`: three assertions go red.
- **KB-AP-8** Expecting an off variant from a `build:cli`-only build: no `dist/curation-off` tree and no `dist/variant-axes.json`; with compliance off (the default) the install refuses before any write (remedy `npm run build:mds`), and only a compliance-on machine still falls through to the curation-on files.
- **KB-AP-9** Handing an agent the whole index, a slice with no marker or footer, or a slice cut by a script: the marker is how the agent finds the full index when the slice misses, and matching a line to a task is judgment that stays with the model.

## Overview

**Decisions reach agents on one route, and curation off removes the route.** The main model (a command, or the orchestrator on a direct delegation) reads the generated `index.md` and hands each agent a slice of it as `DECISIONS_CONTEXT`; an agent reads the full index only at the path the slice's marker names, when its work leaves the slice, and nothing parses the ledger. All the decisions text in the commands and agents sits in curation-on arms that the build resolves into two variants of each prompt: a machine with curation off installs the curation-off variants (no decisions text) and no `devflow:apply-decisions` skill, and `devflow curation --enable/--disable` converges the installed files either way. Only the curation-on variants gate at run time, because a repository can narrow curation off on a machine where it is on.

## Session-start Section 1: the TL;DR, the Index line and the pass rule

`session-start-context` Section 1 emits `--- PROJECT DECISIONS (TL;DR) ---`: the count line from each of `decisions.md` and `pitfalls.md` (`N decisions`, `N pitfalls`, cut from line 1 with sed), then, last, `Index: <ledger root>/.devflow/curation/index.md`. The Index line exists only when `DIRECTIVE_LEDGER_SAFE` admits the ledger root and the index is non-empty with a first line other than `(none)`; builtins only. Every file it reads goes through `df_file_below "$LEDGER_ROOT"`, so one a link leads to reads as absent and is logged once; an index a link leads to gets no Index line, since the model would read the file the link names and pass a slice of it on as `DECISIONS_CONTEXT`. The healing `mkdir -p` of a missing `curation/` runs only where `df_no_symlink_below` admits the path. The section is emitted when either part exists, and not at all while the curation area is paused (hub KB-INV-24): a paused project gets no heal, no TL;DR, no Index line and no Curate directive, only the fixed pause notice as a `systemMessage` on `startup`, `resume` and `clear`. The other sections are in `curation-capture-system-agent`.

**The pass rule follows the Index line** (D-DECISIONS-CHARTER-HANDOFF). `DECISIONS_PASS_RULE` is a static one-line literal (no input interpolated, so no shape gate): decisions are handed on for direct delegations only, workflow skills load their own, and, when the settings line does not say `CURATION=off`, the model reads the index once, then passes each agent that takes `DECISIONS_CONTEXT` the index lines that touch its work, verbatim, behind a `(slice: N of M entries — full index: <the index's path>)` line and with the footer. It is emitted only with an Index line, since without an index there is nothing to pass; the same text reaches the jq and the node envelope. The rule lives here and not in the orchestrator charter: this section is already gated on the machine switch narrowed by the repository, so a curation-off machine or repository never pays for it, and it reaches sessions with ambient off, which the charter never did.

## Consumers of the decisions index

**The defines** (`_decisions.mds`; `authoring_decisions()` lives in `_preamble.mds`, which imports the module as `decisions`):

- `decisions_locate()` runs ONE `git -C "{start}" rev-parse --path-format=absolute --show-toplevel --git-common-dir` from `WORKTREE_PATH` or the cwd and picks `{ledger}`: the main worktree (line 2 without `/.git`, when the output is exactly two absolute lines, line 2 ends `/.git`, and the parent is not HOME and holds a `.devflow/`), else the toplevel (the line after the echoed flag on git < 2.31), else the start directory. It mirrors the hooks' rule (D-PROMPT-ROOT).
- `decisions_gate()` (D-DECISIONS-LEARNING-GATE) is one sentence: when the settings line says `CURATION=off`, set `DECISIONS_CONTEXT` to `(none)` and skip the step before it locates a ledger or reads an index. An unresolvable settings line reads `CURATION=off`, as the fail-closed line does, because a failed resolution cannot show what git tracks. The line also reads `CURATION=off` while git tracks the curation data folders, or does not answer for them: the files there are the repository's own content (the settings resolver asks, hub KB-INV-24). The partial imports nothing from `_settings.mds`: the gate reads the line the host's settings block resolved above, which in a multi-worktree run is the start root's.
- `decisions_load()` is the gate, the locate rule, a read of `{ledger}/.devflow/curation/index.md` (absent or empty gives `DECISIONS_CONTEXT` `(none)`), and, when it is not `(none)`, Step 2: `decisions_slice()`, then the agents that take the key follow `devflow:apply-decisions`.
- `decisions_slice()` (D-DECISIONS-SLICE) is one paragraph: hand each agent that takes `DECISIONS_CONTEXT` a slice, not the whole index: the lines whose title, scope or area touch the files and task it works on, verbatim, led by `(slice: N of M entries — full index: <absolute index path>)` and closed by the index footer. When unsure, include the line: a slice that misses costs one full-index read, one that over-includes costs only its bytes. Siblings over one diff share ONE slice so their prompts stay identical. No script cuts it: the index stays a pre-rendered file read and matching a line to a task is judgment. The fan-out notes in `code-review` (all Review agents) and `plan` (the Design agents of the gap-analysis phase) name that one shared slice, and the Knowledge spawn block in `_knowledge.mds` takes "the slice for these directories".
- `authoring_decisions()` (D-DECISIONS-AUTHORING-STEP) is the same load as a step that the four dynamic hosts expand right after their settings block, so its gate reads a line already resolved; after the read it expands `decisions_slice()` once over the whole run, because the script carries one `DECISIONS_CONTEXT` for every agent. `authoring_preamble()` carries no decisions text. `_engine.mds` passes `DECISIONS_CONTEXT` to Code.
- **Curation-on-only.** `decisions_load()` and `authoring_decisions()` wrap their whole bodies in a curation-on arm, so every expansion of either exists only in the curation-on build. `decisions_gate()`, `decisions_locate()` and `decisions_slice()` carry no arm of their own, since an arm cannot nest: they are leaves, expanded only from inside an arm (those two defines, and release's own on arm), so no curation-off build holds any of them.

**Hosts.** These import `{ decisions_load }`: bug-analysis, code-review, debug, plan, implement, explore, self-review, research, resolve. The four dynamic hosts (dynamic-build, dynamic-plan, dynamic-tickets, dynamic-profile) expand `authoring_decisions()`. release imports only `{ decisions_gate, decisions_locate, decisions_slice }` and expands them in its own Phase 1b on arm around its own index read, copying none of the locate text (`tests/commands/partials-root.test.ts`). A curation-off build keeps the settings block only in the hosts with a consumer other than curation (code-review, debug, dynamic-build, explore, implement, plan, resolve, self-review); in the other hosts it sits inside the on arm.

**Declared receivers only (D-DECISIONS-DECLARED-ONLY).** `DECISIONS_CONTEXT` goes only to an agent type whose source lists it among its inputs: Code, Fix, Refactor, Design, Debug, Knowledge, Research, Review, Harden and Triage. `authoring_decisions()` names Code, Fix, Design, Knowledge, Review and Harden, the declared types among the valid `agentType`s the preamble lists, and says every other type gets none; the engine partial's Code-family prompt rule (a curation-on arm) is what carries the index to Fix spawns. An Evaluate, Synthesize, Validate, Git or Explore spawn carries no index, and release's pass sentence says so for the Validate and Git agents it spawns. Every spawn site of a Code variant in implement, resolve, debug and dynamic-build carries the key, with no exemption by operation, because no Code variant reads the index itself. `tests/decisions/decisions-seam.test.ts` computes the declared set from the agent sources (the three Code variants among them) and holds every Code-family spawn site and every sentence that passes the key to it; a sentence that names no receiver ("to all subsequent agents") fails.

**Agents and the skill.**

- The Code agents (`code.mds`, `fix.mds`, `refactor.mds`) share `agents/_partials/_code.mds`, which each host imports by alias. The partial's `input_core()` carries the `DECISIONS_CONTEXT` input bullet and `decisions_orient()` the step, each in a curation-on arm: when the key is provided, follow `devflow:apply-decisions` on it; an absent key or `(none)` means no decisions context. No Code variant has an index-read fallback of its own, so a spawn that omits the key leaves it with no decisions. It states applied decisions in words, never by ID. Each host keeps its own apply-decisions preload in a curation-on arm of its frontmatter.
- `agents/skim.mds` Step 6 reads the decisions TL;DR (the first line of `{ledger}/.devflow/curation/decisions.md`, `<!-- TL;DR: N decisions -->`, reported as the active decision count) and nothing else of the file. Skim imports no MDS partial, so Step 6 spells the locate rule out in prose: the same one `git -C "{start}" rev-parse --path-format=absolute --show-toplevel --git-common-dir` from `WORKTREE_PATH` or the cwd, then the main worktree, else the toplevel, else `{start}`. A linked worktree therefore reports the main worktree's count; `tests/decisions/command-adoption.test.ts` pins the three tiers in order. Skim's decisions text is curation-on only: the on variant takes a `CURATION` input (`on` or `off`, from the orchestrator's settings line; explore, plan and research pass it; an absent input reads `off`) and Step 6 opens with the skip rule, `off` meaning skip and report `(none)` under "### Active Decisions"; the off variant has no Step 6, no `CURATION` input and no Active Decisions line, and renumbers the summary step so there is no gap.
- The `apply-decisions` skill is a short grep-then-offset reader: it finds an entry's `## ADR-NNN:` or `## PF-NNN:` heading in the file the index footer names with `command grep -nF` (the ledger is git-ignored, so only a shell search finds the line) and Reads that section by offset and a limit of about 25 lines. Its Iron Law allows for a slice (`DECISIONS_CONTEXT` may be a slice; read the full index at the named path only when the work leaves the slice's scope) and Step 1 names the `(slice: …)` marker line; the allowance adds no preload bytes (the ceilings in `tests/guards/code-preload.test.ts` hold). Its Skip Guard is one sentence: skip when `DECISIONS_CONTEXT` is empty, `(none)` or not provided, and never load decisions files otherwise. It has no clause for reading the index when no key arrived: only a slice's marker sends an agent to the full index. The Curate agent does not preload the skill, since its body never reads a decisions index.
- The main model's rule to pass a slice of the index on direct delegations is `DECISIONS_PASS_RULE` (above). The orchestrator charter holds no decisions text.

## Curation variants (D-LEARNING-VARIANTS)

On a machine with curation off the decisions text is ABSENT from every prompt it would have reached. The arms are whole-line markers: `<!-- curation:on -->` keeps its lines only in the curation-on variant, `<!-- curation:off -->` only in the curation-off variant (directly after an on arm it is that arm's else), `<!-- curation:end -->` closes (`VARIANT_MARKER_RE`, `src/core/curation-variants.ts`). A marker may be indented and may sit inside a fence, a list item, a define body or an agent's frontmatter, because MDS passes an HTML comment through untouched; it is removed whole and every other line is kept byte for byte, so a paragraph's blank line goes inside the arm that owns the paragraph.

`splitVariants` (two axes, curation and compliance) runs in `scripts/build-mds.ts` (`materializeOutputs`) on the COMPILED body of each command and agent host, so it adds no compile call: the on variant lands at the host's usual path (`dist/commands/x.md`, `dist/agents/x.md`) and the off variant at `dist/curation-off/{commands,agents}/x.md` (`variantOffRelPath(key, kind, name)`; compliance-armed hosts also get `dist/compliance-off` and `dist/curation-compliance-off`), only for a host with an arm. The build refuses same-axis nesting, interleaved arms, an unopened end, an unclosed or empty arm, a malformed marker, the retired `<!-- learning:` spelling (the `legacy-marker` error) and any marker in a reference module; the build also deletes the retired tree `dist/learning-off` whole; an orphan prune keyed on the files actually written covers every off tree (the total map `OFF_OUTPUT_DIRS`); no marker survives into `dist/`. The hosts with arms are the ones in `CURATION_VARIANT_HOSTS`: the command hosts, and the agent hosts code, fix, refactor, design, debug, knowledge, research, review, harden, skim and triage, each a `.mds` generator host; the three Code hosts get their decisions arms through the shared agent partial, which the split sees expanded because it runs on the compiled body. The other agents hold no decisions text and have no variant; the Curate agent runs only when curation is on. Where a numbered step is dropped the later numbers are on/off pairs, so the off variant has no gap. The one curation token left in an off build is the settings grammar paragraph, which names `CURATION=<on|off>` because the settings line's shape is pinned. The markers map one to one onto a native conditional (`on` is `@if curation:`, `off` is `@else:`, `end` is `@end`) for when MDS can place one inside a fence or an indented line.

## Which variant a machine runs (D-LEARNING-VARIANT-INSTALL)

The machine switch alone decides. `commandSourceDirs(switches, root?)` and `agentSourceDirs(root?, switches = ALL_SWITCHES_ON)` (`src/core/assets.ts`, `VariantSwitches` from `curation-variants.ts`) put `dist/curation-off/<kind>` ahead of the normal order when curation is off (the compliance-off and both-off trees likewise for their switches), so a host with an arm installs its off variant and one without falls through to its single file; `loadShippedAgentDefaults` and the test harness keep reading the on variant, since the shipped model and effort are the same in both. `installViaFileCopy` takes a REQUIRED `curation` and `compliance`, which `devflow init` passes as its settled values, and leaves `CURATION_GATED_SKILLS` (`omitCurationGatedSkills` in `src/core/plugins.ts`) out of the skill loop when it is false. The skill stays owned and required by its plugins in the registry, because the closure guard reasons over the on variant.

`convergeCurationVariants` (`src/targets/claude-code/curation-install.ts`) makes an already-installed tree match the switch. `devflow init` runs it right after the file copy, and `devflow curation --enable/--disable` runs it through `applyCurationToggle` after the switch is written.

- **Roster**: the `.md` files that exist under `dist/curation-off/{commands,agents}` (flat lowercase names, bounded by `MAX_CURATION_ROSTER` per kind), so a new arm needs no edit here. A missing directory (a `build:cli`-only build) warns to run `npm run build:mds` and leaves the installed prompts as they are.
- **Only what is installed**: a file with no installed copy is left alone, so a toggle or a `--plugin` install never adds another plugin's file. A write is byte-compared (a file already holding the target bytes is untouched) and atomic, each item is isolated and every failure is a warning.
- **State carried into the variant before the comparison**: an agent's installed `model:` and `effort:` (D-AGENT-OVERRIDE-CARRY, `withInstalledState`, `carryAgentOverrides`) and `/code-review`'s language-focus stamp (D-LANGUAGE-FOCUS-STAMP). `reapplyAgentMapping` still runs after a toggle that rewrote an agent and stays the authority.
- **The skill**: removed on off; on on, installed only when the effective plugin selection's closure holds it. It is resolved through the installer's own `resolveSkillSource` from the same package root as the variants and swapped in through a staging directory under the Claude directory, never under `skills/`. Only skills and rules have shadows: a shadow of apply-decisions under curation off is dormant (kept in `~/.devflow/skills`, never installed, never deleted) and applied again on enable; commands and agents have none.
- **Skew and failure**: `applyCurationToggle` skips the converge with a "run `devflow init`" message when there is no readable manifest or `manifest.version` differs from the running CLI's (`curationToggleSkew`), since the variants in this package belong to this version. A skip or a failure only warns and never changes the exit code: either mismatch is safe, because an on variant is still gated at run time and an off variant loads no decisions.
- **D-LEARNING-PRELOAD-MACHINE-ONLY** (the apply-decisions preload follows the machine switch and never a repository's narrowing, because the installed agents are machine-wide) is met by the variant: the curation-off agent files do not preload the skill, with no install-time frontmatter rewrite, and the curation-on files keep the preload and the run-time gate. A repository whose `project.json` sets `curation: false` on a curation-on machine therefore changes nothing installed.

## Anti-Patterns

- **KB-AP-1, decisions text outside an arm**: nesting an arm, an empty arm, a marker in a reference module and a mid-line marker all fail the build; a stray `DECISIONS_CONTEXT` bullet, step or pass site outside `<!-- curation:on -->` does not, and it reaches curation-off machines.
- **KB-AP-2 and KB-AP-3, undeclared receivers and a Code index read**: the index is the largest single input a command can give an agent. Name the declared receivers. Do not give Code an index read of its own, or the Skip Guard a clause for one: a Code spawn without the key has no decisions, and every Code spawn carries the key.
- **KB-AP-4, the charter**: the rule belongs in the session-start decisions block, where the machine switch and the repository's narrowing already gate it.
- **KB-AP-5, the preload**: the curation-off variant is the file that carries no preload.
- **KB-AP-9, the whole index**: hand a slice with its marker and footer, cut by the model. The index stays a pre-rendered file read, never built on demand, and matching a line to a task is judgment (LLM-vs-plumbing); a slice with no marker leaves an agent no way to the full index. Over-including costs only bytes, so include the line when unsure.

## Gotchas

- **The switch is install-time, a repository's narrowing is run-time (KB-INV-5).** A repository that narrows curation off changes no installed file; on a curation-on machine the `decisions_gate()` sentence and Skim's `CURATION` skip, both present only in the curation-on variants, are what keep the decisions load from running; a paused curation area narrows the same way, through the settings line, and changes no installed file either. On a curation-off machine no prompt reads `CURATION` at all.
- **Re-init keeps the recorded switch.** `devflow init` seeds the curation value from the manifest; only `--curation` / `--no-curation`, the wizard's answer or `devflow curation --enable/--disable` flips it, and the installed variants follow the settled value.
- **KB-AP-8: no `dist/curation-off` tree means no off variant.** A `build:cli`-only build writes none, nor the variant manifest: with compliance off (the default) the install refuses before any write, and on a compliance-on machine a curation-off install falls through to the curation-on files (still gated at run time); the converge warns to run `npm run build:mds`. The skill is still left out.
- **A converge that changes nothing prints nothing.** The `Installed prompts:` line appears only when a command or agent was rewritten or the skill was installed or removed; a skip because of version skew always warns.
- **KB-AP-7: a host that gains or loses an arm changes the roster.** `CURATION_VARIANT_HOSTS` is asserted against the build's printed `N curation-off variant(s) written` count, the files on disk under `dist/curation-off` and the packed tarball, so all three go red until it is updated.
- **Install surface.** The curation-off variants ride in the package under `dist/curation-off/` and are what a curation-off machine installs in place of the on files; the `devflow:apply-decisions` skill installs on a curation-on machine only.
