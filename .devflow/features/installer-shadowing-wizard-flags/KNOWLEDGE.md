# Wizard Steps, Flags CLI/TUI & Managed-shape Oracle

## Rules

- **KB-AP-1** Never re-derive the display vocabulary at a render site: route through `effectiveDisplay` / `formatFlagValue` (`D-EFFDV`). Literal `unset` appears only where the user typed it (`--set flag=unset`).
- **KB-AP-2** Do not "restore symmetry" between the attribution and compliance gates: `shouldRunAttributionStep` is Advanced-only with no `modePromptShown` and no CLI override, by design.
- **KB-AP-3** The compliance gate keys on `modePromptShown`, never on the mode name, or `--recommended` and the non-TTY fallback lose their promptless contract.
- **KB-AP-4** Never add `attribution` to `templates/settings.json` or `mergeDevflowSettingsTemplate`: the flags pipeline is its only writer, and a second one races it.
- **KB-AP-5** Never hand-roll the managed-shape comparison (`isDeepStrictEqual` against the guard) at a call site: delegate to `settingValueHoldsManagedShape` / `settingHoldsManagedShape`.
- **KB-AP-6** Never define `PromptOutcome` or `WizardPromptIO` locally in a wizard module: import them from `prompt-io.ts`.
- **KB-AP-7** `convergeFlagsIntoSettings` never skips its post-strip key-order restore (`D-KEY-ORDER`): without it a second init moves flag keys behind a key merged after them and re-init stops being a no-op.
- **KB-AP-8** The adoption folds run on PRE-strip content: after `stripFlags` they are vacuous and an externally set `/focus` or a template-written attribution block is lost.
- **KB-AP-9** Never narrow `BooleanFlagDef` with a `target.type` check: `onPayload` stays a union. Use the exported `isEnvBooleanFlag(f)` where the string type matters.
- **KB-AP-10** Wizard step orchestrators never `throw` or `process.exit()`: they return `{kind:'resolved'...}` or `{kind:'cancelled'}` and callers own the cancel idiom.
- **KB-AP-11** `persistFlagConfig` never reports success with an absent manifest, and success is tracked in locals, never read back off the process-wide `process.exitCode`.
- **KB-AP-12** `--enable` / `--disable` are boolean-only: non-boolean flags use `--set`.
- **KB-AP-13** Do not expect `ENTER_ALT` sequences from the flags TUI: it runs inline (`screen: 'inline'`); only agents-view uses the default alt screen.
- **KB-AP-14** `GATE_LEVEL_HINTS` (gate-level-prompts.ts) says what each level does and `GATE_LEVEL_EFFECT` (gates.ts) says which commands read the level: change a hint when what a level does changes, but a command that starts to read the level with no rule that changes a phase changes `GATE_LEVEL_EFFECT` alone, since the hints stay true. A test pins the exact text of both tables and `GATE_LEVEL_MEANINGS`; a change to either table fails it until you check the other and update the pin. One shared table is #551.
- **KB-AP-15** Never default, narrow or heal the stored gate level on a seed or promptless path (no `??` default, no `parseGateLevel` write-back): a stored `null` or malformed value must pass through raw. This holds for a level read from a manifest `readManifest()` refuses, too (KB-INV-13).
- **KB-AP-16** init never writes the personal `gateLevel` in a repository's `.devflow/config.json`: it writes only the manifest `features.gateLevel`, and the personal key still wins where it exists.
- **KB-INV-1** `settingDeleteGuard` protects deletion, not writes: `suppress-attribution` enabled always writes `{"commit":"","pr":""}`, overwriting a custom attribution; disabled deletes the key only when the value deep-equals the managed shape. Test-pinned.
- **KB-INV-2** `settingValueHoldsManagedShape` is the single equality oracle for managed-shape comparisons; `canDeleteSettingKey`, `resolveExistingAttributionSuppression` and the adoption fold all delegate to it.
- **KB-INV-3** The `attribution` settings key is owned exclusively by the flags pipeline (`applyFlags` / `stripFlags` via `convergeFlagsIntoSettings`); a registry-driven test asserts no setting-target key appears in the template.
- **KB-INV-4** `suppress-attribution` (like view-mode) is encoded into `FlagsRecord` BEFORE `convergeFlagsIntoSettings` runs (fold-before-strip).
- **KB-INV-5** Every wizard gate predicate is pure, fully wired, seeded and tested for both init paths.
- **KB-INV-6** `persistFlagConfig` evaluates the settings write and the manifest write independently; neither is skipped by the other's outcome.
- **KB-INV-7** `buildPayload` returns `structuredClone` for object payloads (`D-PAYLOAD-CLONE`): a `FLAG_REGISTRY` entry is never aliased into the caller's settings tree.
- **KB-INV-8** Flag `blurb` and `hint` length caps are enforced by registry-walk tests in `tests/flags.test.ts`, not by TypeScript types.
- **KB-INV-9** A guarded setting flag the manifest has not recorded starts OFF when its settings key already holds a value that is not the managed shape; `respectUserOwnedSettings` (built on `settingHoldsUserValue`) is the one rule, applied by the init seed and by the flags TUI's starting rows, with no flag id special-cased. A flag the manifest records keeps its value, so an explicit enable still wins.
- **KB-INV-10** `settingDeleteGuard` has the type of `onPayload` (`SettingPayload`), so a scalar flag guards its scalar the same way an object flag guards its shape: `subagent-cache-5m` writes `"5m"` to `subagentPromptCacheTtl` and deletes the key only when the value is still `"5m"`, so a user's own `"1h"` survives disable and uninstall.
- **KB-INV-11** `--gate-level` is parsed (`resolveGateLevelInitState`, strict) right after the `--reset`/`--plugin` check and before any write: an invalid level exits 1, `--hud-only --gate-level` exits 1, and so does `--gate-level` with no value (a Commander error: the option is declared `--gate-level <full|standard|lean>`, as `devflow gates --set` is, so the message names the levels).
- **KB-INV-12** The gate-level gate is `shouldRunGateLevelStep`, which delegates to the shared `shouldRunPromptedWizardStep` and keys on `modePromptShown`. It is reached only through `resolveGateLevelForInit`, the only precedence site: `--gate-level`, then the wizard answer, then the carried stored value raw. `runGateLevelStepAt` returns a `GateLevelDecision` (`{level, carried}`), both paths assign it to `gateDecision`, and `applyCliToggles` has no `gateLevel` arm.
- **KB-INV-13** init never writes a gate level the user did not choose. A manifest `readManifest()` refuses (valid JSON with a `features` object and a missing or mistyped required field, or a leading byte-order mark) reads as no manifest, yet still holds a level that `devflow gates` and the settings resolver read. So full init (`carriedGateLevel`) and `--hud-only` carry that raw level (`readStoredGateLevel`) unless a prompt answer, `--gate-level` or `--reset` replaces it, and a manifest that cannot be read is reported with the `devflow gates --set <level>` hint, never written as the default.

## Overview

Three CLI-layer concerns share this KB because they converge on the flags record: the wizard step modules (`compliance-prompts.ts`, `attribution-prompts.ts`, `gate-level-prompts.ts` over the shared `prompt-io.ts` seam), the `devflow flags` command and its inline TUI, and the pure registry pipeline in `src/core/flags.ts` that writes the record into `settings.json`. Core stays UI-agnostic: all I/O-free flag logic lives in `src/core/flags.ts`; the CLI modules own prompts, Commander wiring, settings I/O and manifest persistence, and the init-specific prompt modules (and `init-seed.ts`) live in `src/cli/commands/` rather than `src/core/` for that reason. The tracker wizard step has its own gate and prompt shape and is in the tracker-wiring KB; init-seed (the KB of that name) covers how the seed is computed.

## Shared Wizard Prompt-IO Seam (`prompt-io.ts`)

A one-definition seam owning the shared DI types and the real clack adapters:
- `PromptOutcome<T>` — `{ kind: 'value'; value: T } | { kind: 'cancel' }`.
- `WizardPromptIO` — the base injectable interface: `note(message, title): void` + `select(opts): Promise<PromptOutcome<boolean>>`.
- `clackNote` / `clackSelect<T>` — the real adapters; `clackSelect` narrows away the cancel branch with `p.isCancel` as a type guard, no `as T` cast.
- `AttributionPromptIO` is a type alias of `WizardPromptIO` (a named export kept for tests and callers importing it by name); `CompliancePromptIO`, `TrackerPromptIO` and `GateLevelPromptIO` extend it with their own prompt.
- `shouldRunPromptedWizardStep({mode, modePromptShown, isTTY, hasCliOverride})` — the shared gate table for a step that runs on both wizard paths: CLI override → no; non-TTY → no; Advanced → yes; Recommended → only when `modePromptShown`. The gate-level step delegates to it. The compliance and tracker gates keep their own copies of the table until #554 moves them; the attribution gate is Advanced-only by design and never uses it. The rows are pinned in `tests/prompt-io.test.ts`.

A new wizard step builds on this module rather than redefining those types.

## Compliance Wizard Step (`compliance-prompts.ts`)

CLI-layer module owning all compliance wizard UI:
- `frameworkChoices()` (clack multiselect options from `COMPLIANCE_FRAMEWORKS`), `FRAMEWORK_SELECT_MESSAGE`, `formatFrameworkCatalogue()` (padded catalogue for the `p.note` body), `formatComplianceSummary(enabled, frameworks)` (pure; the canonical home for the compliance state label, re-exported by `init.ts` for backward-compatible test imports).
- `CompliancePromptIO` — `WizardPromptIO` plus `multiselect`; `buildClackCompliancePrompts()` builds the real adapter, translating the cancel symbol into the `PromptOutcome` union.
- `runComplianceStep(opts)` — pure orchestrator, all I/O through `opts.prompts`. Flow: note header → labeled enable select → framework multiselect (`required:false`). Disabling preserves frameworks (defensive copy; returned arrays never alias the seed). Returns `{kind:'resolved', state, messages}` or `{kind:'cancelled'}`.
- `shouldRunComplianceStep({mode, modePromptShown, isTTY, hasCliOverride})` — pure gate: `hasCliOverride` (`--compliance` / `--no-compliance`) → no; non-TTY → no; Advanced → yes; Recommended → only when `modePromptShown`, which is `true` only when the Setup-mode `p.select` actually ran (the `--recommended` flag and the non-TTY fallback never set it). BOTH wizard paths call it. Recommended threads the result via `applyCliToggles(…, { compliance: cliComplianceOverride ?? wizardCompliance })`.

## Attribution Wizard Step (`attribution-prompts.ts`, D27)

Parallel structure to the compliance module with a deliberately different gate:
- `shouldRunAttributionStep({mode, isTTY})` → `isTTY && mode === 'advanced'`. Safe without `modePromptShown` because the Advanced branch itself exits non-zero on non-TTY, so `mode === 'advanced'` only occurs interactively. There is no CLI override: post-install toggling is `devflow flags --enable/--disable suppress-attribution`. The question never runs on Recommended, which carries the seeded value unchanged.
- `buildClackAttributionPrompts()` delegates to the shared `clackNote` / `clackSelect`.
- `attributionSeedFrom(flags: FlagsRecord): boolean` → `true` only for `suppress-attribution === true` (not `as boolean`; undefined, null and false map to false), so `init.ts` passes a real boolean to `p.select`.
- `applyAttributionAnswer(flags, outcome): FlagsRecord` — immutable merge (a new record, never a mutation) and the single merge site; `init.ts` must not duplicate the spread.
- `runAttributionStep({seed, prompts})` — pure orchestrator. Its note names the destructive enable branch ("Yes REPLACES any existing `attribution` value in settings.json, including a custom one") and carries an org AI-disclosure-policy clause.
- **Call site in `init.ts`:** `mode: useRecommended ? 'recommended' : 'advanced'` (never a string literal); one call, in the Advanced path only, via `shouldRunAttributionStep`; `attributionSeedFrom(enabledFlags)` derives the seed and `applyAttributionAnswer(enabledFlags, outcome)` updates `enabledFlags`.

## Gate-Level Wizard Step (`gate-level-prompts.ts`)

Asks for the MACHINE gate level, manifest `features.gateLevel`, the field `devflow gates --set` also writes (`src/cli/commands/gates.ts`). The closed set and parser stay in `src/core/gate-level.ts` (`GATE_LEVELS`, `DEFAULT_GATE_LEVEL`, `parseGateLevel`); this module only imports them.
- **Gate:** `shouldRunGateLevelStep({mode, modePromptShown, isTTY, hasCliOverride})` delegates to the shared `shouldRunPromptedWizardStep` (prompt-io section): `--gate-level` → no; non-TTY → no; Advanced → yes; Recommended → only when `modePromptShown`. Rows: the `shouldRunGateLevelStep` describe of `tests/gate-level-prompts.test.ts` and `tests/prompt-io.test.ts`.
- **Prompt content:** `GATE_LEVEL_HINTS` (one-line effect per level), `gateLevelChoices()` (`GATE_LEVELS` order: full, standard, lean), `formatGateLevelCatalogue()`, `GATE_LEVEL_SELECT_MESSAGE`. The step uses `p.select`, never `p.confirm`, so pressing Enter is an informed keep of a named level.
- **Reading a stored level:** `classifyGateLevel(stored, origin)` is the one classification (`default` | `level` | `malformed` | `unreadable`) behind `describeGateLevel`, `gateLevelPromptSeed`, `formatGateLevelRow` and `formatGateLevelSummary`; a private `appliedLevel` folds it to the level that applies. The prompt starts on the stored level on re-init, on `standard` for `undefined` (first install, no key, `--reset`) or an unreadable level, and on `MALFORMED_GATE_LEVEL_READS_AS` (`full`, from `src/core/gate-level.ts`, held to the settings resolver's fold by a parity test) for a malformed value. `describeGateLevel` adds `(default)` only when nothing is recorded, and shows a malformed value as `invalid (manifest.json; reads as full)`, the words of the `Machine:` line of `devflow gates` (a parity test holds the two), never the raw value.
- **Where the stored level was found:** `StoredGateLevelOrigin` is `manifest` | `rejected` | `unreadable`. `readStoredGateLevel(devflowDir, manifest, reset)` returns `{origin, value}`, the level the run replaces. With a `readManifest()` manifest it is `manifest` and that level. Otherwise the pure `storedGateLevelFromRaw` classifies the raw `readGateManifest` read: `absent`, no key, or `object` (the file changed between reads) → `manifest`, the raw value if any; `rejected` with a level → `rejected`, the raw value untouched; `corrupt` (no `features` object included) or a raw value that fails `JSON.stringify` (nested too deep to write back) → `unreadable`. Under `--reset` the raw level is read for the summary's prior reading only (`unreadable` becomes `manifest`, no value). `carriedGateLevel({manifest, reset, stored, seedLevel})` is what a full init starts from: the seed's level with a `readManifest()` manifest or under `--reset`, else `stored`. `GateManifestState` in `gates.ts` splits `rejected` (init keeps the level unless the run sets another or resets) from `unreadable` (init keeps it only if it can read the file: `readManifest()` has no size bound, so a valid file over 1 MiB is unreadable to gates and readable to init).
- **DI seam:** `GateLevelPromptIO extends WizardPromptIO` with a sibling `selectLevel` (the shared `select` is boolean-typed; widening it would change the seam for every wizard). `buildClackGateLevelPrompts()` delegates to `clackNote` / `clackSelect`.
- **Orchestrators:** `runGateLevelStep({stored, storedOrigin?, prompts})` is pure and returns `{kind:'resolved', level}` or `{kind:'cancelled'}`; its note shows the origin (`rejected`: init replaces the manifest and keeps the level unless another is chosen; `unreadable`: `Current setting: unknown`). `resolveGateLevelForInit({cliLevel, stored, storedOrigin, mode, modePromptShown, isTTY, prompts})` wraps the gate and the step (`storedOrigin` required, so the prompt cannot lose it) and returns `{kind:'resolved', level, carried}`: with no prompt it resolves `cliLevel ?? stored`, `carried` true only for `stored`, so an absent, malformed or `null` value, or a level carried from a rejected manifest, passes through untouched.
- **Boundary:** `resolveGateLevelInitState(option, hudOnly)` returns `undefined` when the flag was absent, else `{ok:true, value}` or `{ok:false, error}`: strict (`Lean` or an empty value is rejected, with `parseGateLevel`'s own error text and no `--gate-level:` prefix), reports a bad value before the `--hud-only` conflict, and refuses `--hud-only` because that path writes no level.
- **Summary:** `formatGateLevelSummary({level, priorLevel, priorOrigin?, kept, manifestWritten})` returns `SummaryLine[]` from the state the run acted on. The recorded level reads "the machine default; change it with devflow gates --set" and appends ` (was X)` when the applied level changed; the comparison is on applied levels, so a malformed value written back as stored, or accepted at the prompt as the `full` it reads as, is no change. If the manifest did not reach disk, a warning names the prior level and says "the gate level did not change". With a `rejected` prior, a warning says init kept the level only when `kept` is true: init carried the stored level (no `--gate-level`, prompt answer or `--reset`), so a chosen level never warns, even an equal one. With an `unreadable` prior, a run that recorded none warns that `standard` applies, with the `devflow gates --set <level>` hint.
- **Call sites in `init.ts`:** `storedGate = readStoredGateLevel(devflowDir, existingManifest, !!options.reset)` follows the manifest read, `carriedGate = carriedGateLevel({...})` follows the seed, and `gateDecision: GateLevelDecision` starts as `{level: carriedGate.value, carried: true}`. The `runGateLevelStepAt(mode)` closure passes `stored: gateDecision.level` and `storedOrigin: carriedGate.origin`, returns the decision and owns the cancel idiom (`p.cancel` + `process.exit(0)`); each path assigns it once, right after the tracker step. It emits no step messages: the summary after the tracker asset summary is the only surface (`kept: gateDecision.carried && carriedGate.origin === 'rejected'`, `priorLevel` and `priorOrigin` from `storedGate`), and the Recommended note adds a `Gate level:` row between `Tracker:` and `View mode:`. The manifest write spreads `gateDecision.level` in only when it is not `undefined`, so a first install, an unreadable manifest without `--gate-level`, and `--reset` record none.
- **`--hud-only`:** it reads `readStoredGateLevel(devflowDir, existingHudManifest, false)`, passes the value to `buildHudOnlyManifest(existing, version, now, refusedGateLevel?)` and, only for a `rejected` or `unreadable` origin, prints the same summary lines with `kept: true`. Over a manifest init can read it says nothing about the gate level.
- **Seed plumbing (`init-seed.ts`):** `FeatureSeed.gateLevel: unknown` is required so the compiler forces every seed site to name it; `resolveSeedFeatures` reads `manifest?.features.gateLevel` with no default operator, `FEATURE_DEFAULTS.gateLevel` is `undefined`, and `applyCliToggles` takes `Partial<Omit<FeatureSeed, 'gateLevel'>>` and passes the seed's raw value through. The seed never reads a rejected manifest's file: that is the init-side override (`carriedGateLevel`).

## Flags Pipeline and the Managed-shape Oracle (`src/core/flags.ts`)

- **Registry types:** `FLAG_REGISTRY` (a `ClaudeCodeFlag` per flag; `auto-compact-window` is an opt-in number flag, unset by default); `FlagDefCommon` carries `blurb` (short trailing-column phrase) and `hint`. `BooleanFlagDef = EnvBooleanFlagDef | SettingBooleanFlagDef` is a discriminated union that provides declaration-site guarantees only: `EnvBooleanFlagDef` compile-constrains `onPayload: string` and `settingDeleteGuard?: never`; `SettingBooleanFlagDef` allows a `SettingPayload` (`string | boolean | Record<string, unknown>`) `onPayload` and an optional `settingDeleteGuard` of the same `SettingPayload` type (`D-GUARD-SCALAR`, so a scalar can be guarded; the oracle's deep-equal handles any JSON value with no second code path). A nested `target.type` check does NOT narrow `onPayload` for consumers, so `isEnvBooleanFlag(f): f is EnvBooleanFlagDef` (exported) is the narrowing predicate. `suppress-attribution` is a `SettingBooleanFlagDef` (target key `attribution`, `onPayload` and `settingDeleteGuard` both `{commit:'',pr:''}`); `subagent-cache-5m` is the scalar one (target key `subagentPromptCacheTtl`, `onPayload` and `settingDeleteGuard` both `"5m"`, default ON, placed right after `prompt-caching-1h`, which it leaves untouched) (`D-SUBAGENT-CACHE-5M`: subagents write 5-minute cache entries while the main session keeps the 1-hour TTL; the registry comment records the vendor-precedence probe, and a Claude Code that predates the setting ignores the key). The registry's size is pinned by the `FLAG_REGISTRY` `toHaveLength` assertion in `tests/flags.test.ts`.
- **Single equality oracle:** `settingValueHoldsManagedShape(flag, value)` is true iff the flag has a `settingDeleteGuard` and the value deep-equals it (`node:util.isDeepStrictEqual`); `settingHoldsManagedShape(settingsJson, flagId)` reads `settings.json` and delegates; its mirror `settingHoldsUserValue(settingsJson, flagId)` is true when a guarded setting flag's key is present (`hasOwnProperty`, so an explicit `null` counts) with a value that is not the managed shape, and false for malformed JSON, a non-object root, an unknown or unguarded flag or an absent key. `respectUserOwnedSettings(flags, manifestFlags, settingsSnapshot)` (`D-ADOPT-RESPECTS-USER`, pure) sets such a flag `false` when the manifest does not record it, so the converge pipeline neither writes nor deletes the user's value. `canDeleteSettingKey` (module-private, `D-ATTR-GUARD`) is shared by `applyFlags`' neutral branch and `stripFlags` and delegates to the oracle. `resolveExistingAttributionSuppression` (init-seed KB) and the Step 2b adoption fold delegate too.
- **`convergeFlagsIntoSettings(settingsJson, record, {viewModeExplicit, ownedRecord?})`** is the fold-before-strip pipeline; both `init.ts` and `persistFlagConfig` MUST call it instead of `stripFlags` + `applyFlags` directly, so the invariant lives in the pipeline. Steps: (1) fold view-mode via `resolveFinalViewMode`, so an externally set `/focus` survives unless `viewModeExplicit`; (2) fold existing settings values into the record for unclaimed valued (enum/number/string) flags — "claimed" is decided by `ownedRecord` (omitted → the record itself, the `persistFlagConfig` path; `null` → nothing owned, fresh install; the pre-seed manifest flags on the init path), and boolean flags are never folded at this step; (2b, `D-ATTR-ADOPT`) adopt guarded boolean settings whose pre-strip on-disk value matches the managed shape, only when the record does not already claim the flag (a claimed `false` or `null` still deletes the block), so a template-written attribution block is not stripped unconditionally on first init; (3) `stripFlags` then `applyFlags` over the folded record; (4) `orderKeysLike` restores the pre-strip key order, top-level and inside `env` (`D-KEY-ORDER`: strip-then-apply re-adds every managed key at the end, and the security deny list merged AFTER the flags appends `permissions`, so without the restore the second init reorders and re-init is no longer byte-for-byte stable). Uninstall calls `stripFlags` directly with no record, preserving its full-sweep semantics.
- **Registry adoption of an on-disk key:** the day a settings key that already ships on disk becomes registry-managed, it must be adopted before the strip pass; the presence of `settingDeleteGuard` is the signal and Step 2b the mechanism.
- **Ownership contract:** the guarded deletion is the prove-you-wrote-it contract (only remove a key whose value is the devflow-managed shape). Its corollary — a guard protects deletion, not overwrite — is why enable overwrites a custom attribution while disable preserves one.

## Flags CLI (`src/cli/commands/flags.ts`)

- **`createFlagsCommand()`** is the root Commander for `devflow flags` (a fresh instance per call; `flagsCommand` is the singleton `src/cli.ts` imports). Options: `--list`, `--status`, `--enable <ids>`, `--disable <ids>`, `--set <assignment>` (repeatable), `--unset <ids>`; bare invocation on a TTY launches the TUI, on non-TTY it prints the status table and exits 1. Flags resolve through `findFlag(id)` from core (unknown IDs error).
- **`readSettingsSafe`** returns `{ok, content}` / `{ok:false, reason}` and never silently falls back to `{}` on malformed JSON (that would clobber the user's settings); a root that is not a JSON object is rejected. ENOENT yields `{}`. `loadFlagContext` is the one shared load path for the mutating branches.
- **`persistFlagConfig(claudeDir, devflowDir, settingsContent, newRecord, manifest, {viewModeExplicit})`** runs `convergeFlagsIntoSettings`, writes `settings.json` (atomically) and `manifest.json` (`features.flags` = the FOLDED record, so adopted values persist and the two stay in sync) independently, and returns a discriminated `PersistResult`: `{ok:true}`, `{ok:false, failed:['settings'|'manifest'...]}`, or `{ok:false, reason:'no-manifest'}` — an absent manifest is a failure, not a no-op, because "Flags saved." with an unrecorded selection is reverted by the next init. Callers print success only on `ok === true`. `applyTuiResult(result, freshSettingsContent, manifest, claudeDir, devflowDir)` (exported) derives `viewModeExplicit` from whether the view-mode row changed and returns `'saved' | 'unchanged' | PersistResult failure`.
- **`handleBare` builds the TUI's starting rows** with `buildFlagRows(respectUserOwnedSettings(record, record, settingsContent))` (`D-ADOPT-RESPECTS-USER`): passing the record as its own manifest view means only flags it does not yet record can flip, so an upgrade that has not run init yet shows an unrecorded `subagent-cache-5m` as OFF when `settings.json` holds the user's own `"1h"`, and a Save does not write `"5m"` over it. The settings snapshot is read in `handleBare`, so the reducer and renderer stay pure; `tests/flags-cli.test.ts` drives it with a mocked `runFlagsTui` that captures the rows.
- **Display vocabulary (`D-EFFDV`, one definition, every surface via `effectiveDisplay`):** `--enable` / `--disable` confirmations call `formatFlagValue` (`true` → `on`, `false` → `off`); `--set` confirmations route active values through `formatFlagValue` and echo literal `unset` for a `null` input at the call site (the user typed that word); `formatStatusRows` (the non-TTY status table, sanitised with `sanitizeCell`) renders not-adopted rows as `not adopted — default: <effective text> applies on next devflow init` using `effectiveDisplay(flag, neutralValueOf(flag)).text`; `--list` prints `upstream default: N` for number flags with `upstreamDefault`, else the `defaultValue` string or `none` (never `unset`).

## Flags TUI (`src/cli/flags-view/`, `src/cli/tui/`)

An interactive editor launched exclusively by `devflow flags` bare on a TTY (D40: init applies flags non-interactively in every path). It runs in **inline mode**, rendering in place in the scroll buffer.
- **`flags-view/state.ts`** — the pure state machine. Exported: `buildFlagRows(record)` (rows from the live `FlagsRecord`; each `FlagRow` holds `id`, the `tui` value, `hint`, and `blurb` sourced from `flag.blurb` at build time, so there is no registry reach-back at render time), `collectFlagRecord(rows)` (the inverse, via `tuiToRecord` per row), `reduce(state, key) → {state, done, saved}`, `resizeViewport`, `BUFFER_MAX_LEN`. Private helpers: `buildStops`, `cycleForward` / `cycleBackward`, `enterEdit` / `commitEdit` / `insertChar` / `reduceEditMode` (inline text edit for enum and string flags), `adjustViewport`. `recordToTui` / `tuiToRecord` live in `core/flags.ts`: the TUI uses `null` as the "devflow default" stop and `tuiToRecord` maps it back to `neutralValueOf`.
- **`flags-view/render.ts`** — frame renderer. Column layout at the 80-col reference: PREFIX 2 (cursor mark), LABEL 27, DIRTY 2 (`● `), VALUE 16, BLURB 30 (dim trailing column, header `HINT`, omitted when `blurbW === 0`); VALUE + BLURB preserve the prior single-VALUE-column total, and all widths scale with terminal width (`Math.min(1, cols/80)`). `formatValue` delegates to `effectiveDisplay` for null/neutral values (`dim(...text)`, with ` (default)` appended for number flags); `true` → green `on`, `false` → yellow `off`; a non-boolean active value is `bold` when it deviates from the devflow default, else plain (`D-BLURB`).
- **`tui/cells.ts`** — shared ANSI-aware cell helpers: `sanitizeCell` (strips control characters; prevents terminal injection), `padToVisible`, `truncateVisible`.
- **`flags-view/terminal.ts`** — `runFlagsTui` passes `screen: 'inline'` to `runTui` (`D-INLINE`); the intent type is closed so a new `FlagsIntent` member is a compile error.
- **`tui/terminal.ts`** — the generic `runTui<S,A,C>` driver. `RunTuiSpec.screen?: 'alt' | 'inline'` defaults to `'alt'` (agents-view); inline mechanics: the first frame writes lines directly, later frames use `cursorUp(prevLineCount - 1) + \r`, rewrite and `ERASE_BELOW`; on exit it cursor-ups to the frame top and uses `ERASE_BELOW` + `SHOW_CURSOR`, erasing the widget so the caller's clack flow continues uninterrupted. `INLINE_MARGIN = 2` lines stay free below the widget so the shell prompt is never clobbered (height clamped to `stdout.rows - INLINE_MARGIN`). `cursorUp(n)` returns `ESC[nA` for `n > 0` and an empty string otherwise, so callers need no guard.

## Anti-Patterns

- **KB-AP-1** Four render sites (TUI `formatValue`, the `--enable` / `--disable` confirmation, the `--status` not-adopted message, `--list`'s `defaultLabel`) all route through `effectiveDisplay`; a fifth that hand-codes on/off or shows `unset` creates vocabulary drift.
- **KB-AP-2** The compliance gate runs on interactive Recommended (`modePromptShown: true`); the attribution gate never does. The divergence is design intent, documented in `attribution-prompts.ts`.
- **KB-AP-4** The template merge runs BEFORE the flags pipeline, so a template-written value would be immediately overwritten, or on the off path leave a stale block. Single ownership is enforced by omission from the template and the merge function and by a registry-driven test in `tests/post-install-merge.test.ts`.
- **KB-AP-5** `resolveExistingAttributionSuppression` and the Step 2b fold both use the oracle; a hand-rolled copy drifts.
- **KB-AP-7** Skipping the restore reintroduces the re-init non-idempotency (#388 AC-3).
- **KB-AP-14** The tables differ in shape (`GATE_LEVEL_HINTS` a per-level `Record` that says what a level does, `GATE_LEVEL_EFFECT` one sentence that says which commands read the level), so TypeScript cannot flag drift. The `the init prompt and devflow gates describe the same levels` describe in `tests/gate-level-prompts.test.ts` pins the exact text of `GATE_LEVEL_HINTS`, `GATE_LEVEL_EFFECT` and `GATE_LEVEL_MEANINGS` (a change to either table fails it until the other is checked and the pin updated; the hints change only when what a level does changes, and a command that starts to read the level with no phase rule changes `GATE_LEVEL_EFFECT` alone). Further rows check the shared clauses only: the level sets, the malformed fold, the lint-pack level, the levels with fewer review focuses and the levels that skip Polish; a one-sided edit to another clause is caught by the pin alone.
- **KB-AP-15** `manifest?.features.gateLevel ?? DEFAULT` turns a stored `null` into `standard`, and init would then write that over a value every reader folds to `full`, silently lowering the level. So `FeatureSeed.gateLevel` is raw, the promptless path is `cliLevel ?? stored` (the only `??`, and `cliLevel` is a parsed level or `undefined`), and an absent key stays out of the manifest write. The same holds for a level read from a rejected manifest (`StoredGateLevel.value` stays raw) and for `buildHudOnlyManifest`'s `refusedGateLevel`.
- **KB-AP-16** The machine level and the personal level are different keys: the wizard text and the summary line say "the machine default", and `tests/init-gate-level-e2e.test.ts` pins that init leaves a repository config without `gateLevel` alone and keeps an existing personal key.

## Gotchas

- **KB-INV-1** `settingDeleteGuard` is test-pinned asymmetric: with a custom attribution block (for example an org name) a flag-disable preserves it and a flag-enable overwrites it. The wizard note says so.
- **KB-AP-9** After `if (f.target.type === 'env')`, `f` is still `BooleanFlagDef` and `f.onPayload` remains `string | boolean | Record<string, unknown>`.
- **`--set flag=unset`** is parsed to `null` by `parseFlagValueInput`; the `handleSet` confirmation special-cases `null → 'unset'` so the user sees their own word. It is the only place `unset` still reaches user-facing output.
- **KB-AP-13** A flags TUI test expecting `ENTER_ALT` fails for `runFlagsTui` but passes for agents-view tests; use `screen: 'alt'` explicitly when testing alt-screen behaviour.
- **Selective uninstall never strips flags** (`runCleanupPhase` only), so flag state persists when individual plugins are removed (uninstall KB).
- **KB-INV-4 fold timing:** a record that already has `suppress-attribution: false` or `null` still deletes the block; the fold only claims unclaimed flags.
- **KB-INV-12 wiring test is source text:** the `init.ts wiring` describe in `tests/gate-level-prompts.test.ts` regex-matches `init.ts`: one `resolveGateLevelForInit({` call, one `gateDecision = await runGateLevelStepAt(...)` per path and no other assignment beside the `let`, no `Promise<void>` closure type, and these lines verbatim: `mode,`, `modePromptShown,`, `stored: gateDecision.level,`, `storedOrigin: carriedGate.origin,`, the `carriedGateLevel` inputs and the `kept:` line (a literal mode would collapse the gate table). Renaming or reformatting fails it by design.
- **Malformed stored level:** the prompt starts on `full`; its note and the summary show `invalid (manifest.json; reads as full)`, never the raw value. A promptless path keeps the value as written. Accepting the prompt records `full` with no `(was X)`, since the applied level did not change.
- **Rejected and unreadable manifests (KB-INV-13):** a promptless init over a rejected manifest keeps the raw level and warns; a prompt answer replaces it, no warning; `--reset` removes it and names it as `(was full)`, no warning; `--gate-level` replaces it. Over an unreadable one a promptless init writes no level and warns with the hint. Pinned in `tests/init-gate-level-e2e.test.ts`.
- **KB-INV-11 `--hud-only` writes early:** `--hud-only` writes before the wizard, so the `--gate-level` parse sits above every write; an invalid value leaves an existing install byte-for-byte unchanged (`tests/init-gate-level-e2e.test.ts`).
- **Test fixtures must match runtime shapes:** `tests/init-e2e-flags.test.ts` drives subprocess e2e tests over the real init settings pass.
