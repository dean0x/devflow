# Wizard Steps, Flags CLI/TUI & Managed-shape Oracle

## Rules

- **KB-AP-1** Never re-derive the display vocabulary at a render site: route through `effectiveDisplay` / `formatFlagValue` (`D-EFFDV`). Literal `unset` appears only where the user typed it (`--set flag=unset`).
- **KB-AP-2** Do not "restore symmetry" between the attribution and compliance gates: `shouldRunAttributionStep` is Advanced-only with no `modePromptShown` and no CLI override, by design.
- **KB-AP-3** The compliance gate keys on `modePromptShown`, never on the mode name, or `--recommended` and the non-TTY fallback lose their promptless contract.
- **KB-AP-4** Never add `attribution` to `templates/settings.json` or `mergeDevflowSettingsTemplate`: the flags pipeline is its only writer, and a second one races it.
- **KB-AP-5** Never hand-roll the managed-shape comparison (`isDeepStrictEqual` against the guard) at a call site: delegate to `settingValueHoldsManagedShape` / `settingHoldsManagedShape`.
- **KB-AP-6** Never define `PromptOutcome` or `WizardPromptIO` locally in a wizard module: import them from `prompt-io.ts`.
- **KB-AP-7** `convergeFlagsIntoSettings` never skips its post-strip key-order restore (`D-KEY-ORDER`): without it a second init moves flag keys behind a key merged after them and re-init stops being a no-op.
- **KB-AP-8** The adoption folds run on PRE-strip content: after `stripFlags` they are vacuous and an externally set `/focus` or a template-written attribution block is lost.
- **KB-AP-9** Never narrow `BooleanFlagDef` with a `target.type` check: `onPayload` stays a union. Use the exported `isEnvBooleanFlag(f)` where the string type matters.
- **KB-AP-10** Wizard step orchestrators never `throw` or `process.exit()`: they return `{kind:'resolved'...}` or `{kind:'cancelled'}` and callers own the cancel idiom.
- **KB-AP-11** `persistFlagConfig` never reports success with an absent manifest, and success is tracked in locals, never read back off the process-wide `process.exitCode`.
- **KB-AP-12** `--enable` / `--disable` are boolean-only: non-boolean flags use `--set`.
- **KB-AP-13** Do not expect `ENTER_ALT` sequences from the flags TUI: it runs inline (`screen: 'inline'`); only agents-view uses the default alt screen.
- **KB-AP-14** `GATE_LEVEL_HINTS` (gate-level-prompts.ts) are short one-idea labels; `GATE_LEVEL_EFFECT` (gates.ts) holds the per-effect detail and the commands that read the level. A hint changes only when what a level checks changes; a command that reads the level with no phase rule changes `GATE_LEVEL_EFFECT` alone. A test pins both tables and `GATE_LEVEL_MEANINGS`.
- **KB-AP-15** Never default, narrow or heal the stored gate level on a seed or promptless path (no `??` default, no `parseGateLevel` write-back): a stored `null` or malformed value must pass through raw. This holds for a level read from a manifest `readManifest()` refuses, too (KB-INV-13).
- **KB-AP-16** init never writes the personal `gateLevel` in a repository's `.devflow/config.json`: it writes only the manifest `features.gateLevel`, and the personal key still wins where it exists.
- **KB-INV-1** `settingDeleteGuard` protects deletion, not writes: `suppress-attribution` enabled always writes `{"commit":"","pr":""}`, overwriting a custom attribution; disabled deletes the key only when the value deep-equals the managed shape. Test-pinned.
- **KB-INV-2** `settingValueHoldsManagedShape` is the single equality oracle for managed-shape comparisons; `canDeleteSettingKey`, `resolveExistingAttributionSuppression` and the adoption fold all delegate to it.
- **KB-INV-3** The `attribution` settings key is owned exclusively by the flags pipeline (`applyFlags` / `stripFlags` via `convergeFlagsIntoSettings`); a registry-driven test asserts no setting-target key appears in the template.
- **KB-INV-4** `suppress-attribution` (like view-mode) is encoded into `FlagsRecord` BEFORE `convergeFlagsIntoSettings` runs (fold-before-strip).
- **KB-INV-5** Every wizard gate predicate is pure, fully wired, seeded and tested for both init paths.
- **KB-INV-6** `persistFlagConfig` evaluates the settings write and the manifest write independently; neither is skipped by the other's outcome.
- **KB-INV-7** `buildPayload` returns `structuredClone` for object payloads (`D-PAYLOAD-CLONE`): a `FLAG_REGISTRY` entry is never aliased into the caller's settings tree.
- **KB-INV-8** Flag `blurb` and `hint` length caps are enforced by registry-walk tests in `tests/flags.test.ts`, not by TypeScript types.
- **KB-INV-9** A guarded flag the manifest has not recorded starts OFF when its settings key already holds a value that is not the managed shape; `respectUserOwnedSettings` is the one rule, applied by the init seed and the flags TUI's starting rows and save, with no flag id special-cased. A recorded flag keeps its value, so an explicit enable still wins.
- **KB-INV-10** `settingDeleteGuard` has the type of `onPayload` (`SettingPayload`), so a scalar flag guards its scalar the same way an object flag guards its shape: `subagent-cache-5m` deletes `subagentPromptCacheTtl` only while it is still `"5m"`, so a user's own `"1h"` survives disable and uninstall.
- **KB-INV-11** `--gate-level` is parsed strictly (`resolveGateLevelInitState`) right after the `--reset`/`--plugin` check and before any write: an invalid level, `--hud-only --gate-level` and a missing value all exit 1.
- **KB-INV-12** The gate is `shouldRunGateLevelStep` (shared `shouldRunPromptedWizardStep`, keyed on `modePromptShown`), reached only through `resolveGateLevelForInit`, the only precedence site: `--gate-level`, then the wizard answer, then the carried stored value raw. `applyCliToggles` has no `gateLevel` arm.
- **KB-INV-13** init never writes a gate level the user did not choose. A manifest `readManifest()` refuses (a missing or mistyped required field, or a leading byte-order mark) reads as no manifest yet still holds a level that `devflow gates` reads. Full init (`carriedGateLevel`) and `--hud-only` carry that raw level (`readStoredGateLevel`) unless a prompt answer or `--gate-level` replaces it or `--reset` removes it; an unreadable manifest is reported with the `devflow gates --set <level>` hint, never written as the default.
- **KB-AP-17** clack `note()` never wraps and pads every row to the longest line, so one long line widens the whole box: a gate-level hint stays short with no line break and every note line stays within the note cap (`collectGateLevelPromptLengthDefects`).
- **KB-AP-18** Never decide "Code Mode / proxy / traffic is on" with a local check or word a Code Mode message inline: `src/core/code-mode.ts` owns the predicates and the fixed message constants, and tests pin the text.
- **KB-AP-19** A flags write that can turn `code-mode` on never runs before `checkCodeModeWrite`: every mutating branch (`--enable`, `--set`, `--unset`, the TUI save) preflights first, and the TUI save re-derives an unedited `code-mode` row from fresh settings.
- **KB-AP-20** A read-only flags or Code Mode read never heals or probes: use `readManifest(dir, {heal: false})` or the raw `readGateManifest`, and never contact the relay.
- **KB-AP-21** Raw readers of settings, manifest or proxy-state files use `readFileBytes(path, maxBytes)`, never a bare `fs.readFile`: it refuses special files and oversize input.
- **KB-INV-14** An env flag with `deleteOnlyOwnPayload` owns only its exact on payload (`holdsOwnEnvPayload`): any other present value at its key is the user's (`holdsUserEnvValue`), is never deleted, and reads as off. `code-mode` is the only such flag.
- **KB-INV-15** `convergeFlagsIntoSettings` folds guarded env payloads BEFORE the strip (Step 2c): an unclaimed exact own payload is adopted as on; a record `true` over a user env value folds to `false` unless the write lists the id in `explicitOn`, which only the off-to-on preflight (`turnsOnCodeMode`) fills. Init passes none.
- **KB-INV-16** Code Mode and the Devflow proxy are refused together in both directions: flags CLI and TUI refuse off-to-on while the proxy is on (`CODE_MODE_ENABLE_REFUSAL`); `devflow proxy` enable refuses while Code Mode is on (`PROXY_ENABLE_REFUSAL`). A requested-on write with an unreadable `settings.json` is refused (`CODE_MODE_READ_FAILURE`); turning off is never blocked by a read failure.
- **KB-INV-17** Blockers (`codeModeBlockers`) show only while Code Mode is on and describe the FINAL state: `writeTimeWarnings` ignores the before-state. Init warns from the converged record and post-preflight proxy state (`initCodeModeWarnings`).
- **KB-INV-18** `readCodeModeSignals` reads local files only: an unreadable `proxy.json` counts as proxy on, an absent or corrupt manifest is ignored, a null `devflowDir` limits it to the settings `env`, and an unrelated manifest defect never erases a readable `flags` record or `proxy` switch (`codeModeManifestSignals`).

## Overview

Three CLI-layer concerns share this KB because they converge on the flags record: the wizard step modules (`compliance-prompts.ts`, `attribution-prompts.ts`, `gate-level-prompts.ts` over the shared `prompt-io.ts` seam), the `devflow flags` command and its inline TUI, and the pure registry pipeline in `src/core/flags.ts` that writes the record into `settings.json`. Core stays UI-agnostic: all I/O-free flag logic lives in `src/core/flags.ts`; the CLI modules own prompts, Commander wiring, settings I/O and manifest persistence; for that reason the init-specific prompt modules (and `init-seed.ts`) live in `src/cli/commands/`, not `src/core/`. The tracker step is in the tracker-wiring KB; the init-seed KB covers the seed.

## Shared Wizard Prompt-IO Seam (`prompt-io.ts`)

One definition of the shared DI types and the real clack adapters; a new wizard step builds on it rather than redefining them:
- `PromptOutcome<T>` — `{ kind: 'value'; value: T } | { kind: 'cancel' }`.
- `WizardPromptIO` — the base injectable interface: `note(message, title): void` + `select(opts): Promise<PromptOutcome<boolean>>`.
- `clackNote` / `clackSelect<T>` — the real adapters; `clackSelect` narrows away the cancel branch with `p.isCancel` as a type guard, no `as T` cast.
- `AttributionPromptIO` is a named alias of `WizardPromptIO`; `CompliancePromptIO`, `TrackerPromptIO` and `GateLevelPromptIO` extend it with their own prompt.
- `shouldRunPromptedWizardStep({mode, modePromptShown, isTTY, hasCliOverride})` — the shared gate table for a step that runs on both wizard paths: CLI override → no; non-TTY → no; Advanced → yes; Recommended → only when `modePromptShown`. The gate-level step delegates to it. The compliance and tracker gates keep their own copies of the table until #554 moves them; the attribution gate is Advanced-only by design and never uses it. The rows are pinned in `tests/prompt-io.test.ts`.


## Compliance Wizard Step (`compliance-prompts.ts`)

CLI-layer module owning all compliance wizard UI: `frameworkChoices()`, `FRAMEWORK_SELECT_MESSAGE`, `formatFrameworkCatalogue()` and `formatComplianceSummary(enabled, frameworks)` (the canonical home of the state label, re-exported by `init.ts` for test imports).
- `CompliancePromptIO` is `WizardPromptIO` plus `multiselect`. `runComplianceStep(opts)` is a pure orchestrator (note header, enable select, framework multiselect with `required:false`); disabling preserves frameworks and returned arrays never alias the seed. It returns `{kind:'resolved', state, messages}` or `{kind:'cancelled'}`.
- `shouldRunComplianceStep({mode, modePromptShown, isTTY, hasCliOverride})` — pure gate: `hasCliOverride` (`--compliance` / `--no-compliance`) → no; non-TTY → no; Advanced → yes; Recommended → only when `modePromptShown`, which is `true` only when the Setup-mode `p.select` actually ran (the `--recommended` flag and the non-TTY fallback never set it). BOTH wizard paths call it. Recommended threads the result via `applyCliToggles(…, { compliance: cliComplianceOverride ?? wizardCompliance })`.

## Attribution Wizard Step (`attribution-prompts.ts`, D27)

Parallel structure to the compliance module with a deliberately different gate:
- `shouldRunAttributionStep({mode, isTTY})` is `isTTY && mode === 'advanced'`: safe without `modePromptShown` because the Advanced branch exits non-zero on non-TTY. There is no CLI override (post-install: `devflow flags --enable/--disable suppress-attribution`), and Recommended carries the seeded value unchanged.
- `attributionSeedFrom(flags)` is `true` only for `suppress-attribution === true`, so `init.ts` passes a real boolean to `p.select`. `applyAttributionAnswer(flags, outcome)` is the single immutable merge site; `init.ts` must not duplicate the spread.
- `runAttributionStep({seed, prompts})` is a pure orchestrator; its note names the destructive enable branch ("Yes REPLACES any existing `attribution` value in settings.json, including a custom one") and an org AI-disclosure-policy clause.
- **Call site in `init.ts`:** `mode: useRecommended ? 'recommended' : 'advanced'` (never a string literal); one call, Advanced path only, via `shouldRunAttributionStep`, seeded by `attributionSeedFrom(enabledFlags)` and merged by `applyAttributionAnswer`.

## Gate-Level Wizard Step (`gate-level-prompts.ts`)

Asks for the MACHINE gate level, manifest `features.gateLevel`, the field `devflow gates --set` also writes (`src/cli/commands/gates.ts`). The closed set and parser stay in `src/core/gate-level.ts` (`GATE_LEVELS`, `DEFAULT_GATE_LEVEL`, `parseGateLevel`); this module only imports them.
- **Gate:** `shouldRunGateLevelStep({mode, modePromptShown, isTTY, hasCliOverride})` delegates to the shared `shouldRunPromptedWizardStep` (prompt-io section): `--gate-level` → no; non-TTY → no; Advanced → yes; Recommended → only when `modePromptShown`. Rows: `tests/gate-level-prompts.test.ts` and `tests/prompt-io.test.ts`.
- **Prompt content:** `GATE_LEVEL_HINTS` (a short label per level), `gateLevelChoices()` (`GATE_LEVELS` order), `formatGateLevelCatalogue()`, `GATE_LEVEL_SELECT_MESSAGE`. The step uses `p.select`, never `p.confirm`, so Enter is an informed keep of a named level.
- **Reading a stored level:** `classifyGateLevel(stored, origin)` is the one classification (`default` | `level` | `malformed` | `unreadable`) behind `describeGateLevel`, `gateLevelPromptSeed`, `formatGateLevelRow` and `formatGateLevelSummary`. The prompt starts on the stored level on re-init, on `standard` for `undefined` (first install, no key, `--reset`) or an unreadable level, and on `MALFORMED_GATE_LEVEL_READS_AS` (`full`, `src/core/gate-level.ts`, held to the settings resolver's fold by a parity test) for a malformed value. A malformed value shows as `invalid (manifest.json; reads as full)`, the words of the `Machine:` line of `devflow gates` (parity test); accepting the prompt records `full`, no `(was X)`.
- **Where the stored level was found:** `StoredGateLevelOrigin` is `manifest` | `rejected` | `unreadable`. `readStoredGateLevel(devflowDir, manifest, reset)` returns `{origin, value}`, the level the run replaces: `manifest` with a `readManifest()` manifest, else the pure `storedGateLevelFromRaw` classifies the raw `readGateManifest` read (`absent`, no key or `object` → `manifest`; `rejected` with a level → `rejected`, value untouched; `corrupt` or a value that fails `JSON.stringify` → `unreadable`). Under `--reset` the raw level feeds the summary's prior reading only. `carriedGateLevel({manifest, reset, stored, seedLevel})` is a full init's start: the seed's level with a `readManifest()` manifest or under `--reset`, else `stored`. `GateManifestState` in `gates.ts` splits `rejected` (init keeps the level) from `unreadable` (kept only if init can read the file; `readManifest()` has no size bound, so a valid file over `MAX_MANIFEST_BYTES` in `src/core/gate-level.ts` is unreadable to gates and readable to init).
- **DI seam:** `GateLevelPromptIO extends WizardPromptIO` with a sibling `selectLevel` (the shared `select` is boolean-typed; widening it would change every wizard). `buildClackGateLevelPrompts()` delegates to `clackNote` / `clackSelect`.
- **Orchestrators:** `runGateLevelStep({stored, storedOrigin?, prompts})` is pure and returns `{kind:'resolved', level}` or `{kind:'cancelled'}`; its note names every command `GATE_LEVEL_EFFECT` lists (a test checks it) and shows the origin. `resolveGateLevelForInit({cliLevel, stored, storedOrigin, mode, modePromptShown, isTTY, prompts})` wraps the gate and the step (`storedOrigin` required, so the prompt cannot lose it) and returns `{kind:'resolved', level, carried}`: with no prompt it resolves `cliLevel ?? stored`, `carried` true only for `stored`, so an absent, malformed or `null` value, or one from a rejected manifest, passes through untouched.
- **Boundary:** `resolveGateLevelInitState(option, hudOnly)` returns `undefined` when the flag was absent, else `{ok:true, value}` or `{ok:false, error}`: strict (`Lean` or an empty value is rejected with `parseGateLevel`'s own error text), reports a bad value before the `--hud-only` conflict, and refuses `--hud-only` because that path writes no level.
- **Summary:** `formatGateLevelSummary({level, priorLevel, priorOrigin?, kept, manifestWritten})` returns `SummaryLine[]` from the state the run acted on. The recorded level reads "the machine default; change it with devflow gates --set" and appends ` (was X)` when the applied level changed (a malformed value written back as stored, or accepted as the `full` it reads as, is no change). A manifest that did not reach disk warns that the gate level did not change. A `rejected` prior warns that init kept the level only when `kept` is true (a chosen level never warns); an `unreadable` prior with no level recorded warns that `standard` applies, with the `devflow gates --set <level>` hint.
- **Call sites in `init.ts`:** `storedGate = readStoredGateLevel(...)` follows the manifest read, `carriedGate = carriedGateLevel({...})` follows the seed, and `gateDecision: GateLevelDecision` starts as `{level: carriedGate.value, carried: true}`. The `runGateLevelStepAt(mode)` closure passes `stored: gateDecision.level` and `storedOrigin: carriedGate.origin` and owns the cancel idiom (`p.cancel` + `process.exit(0)`); each path assigns it once, right after the tracker step. The summary after the tracker asset summary is the only surface (`kept: gateDecision.carried && carriedGate.origin === 'rejected'`), and the Recommended note adds a `Gate level:` row between `Tracker:` and `View mode:`. The manifest write spreads `gateDecision.level` in only when it is not `undefined`, so a first install, an unreadable manifest without `--gate-level`, and `--reset` record none.
- **`--hud-only`:** it reads `readStoredGateLevel(devflowDir, existingHudManifest, false)`, passes the value to `buildHudOnlyManifest(existing, version, now, refusedGateLevel?)` and prints the summary lines with `kept: true` only for a `rejected` or `unreadable` origin.
- **Seed plumbing (`init-seed.ts`):** `FeatureSeed.gateLevel: unknown` is required so every seed site names it; `resolveSeedFeatures` reads `manifest?.features.gateLevel` with no default operator, and `applyCliToggles` takes `Partial<Omit<FeatureSeed, 'gateLevel'>>`. The seed never reads a rejected manifest's file: that is the init-side override (`carriedGateLevel`).

## Flags Pipeline and the Managed-shape Oracle (`src/core/flags.ts`)

- **Registry types:** `FLAG_REGISTRY` holds a `ClaudeCodeFlag` per flag (`auto-compact-window` is an opt-in number flag, unset by default); `FlagDefCommon` carries `blurb` and `hint`. `BooleanFlagDef = EnvBooleanFlagDef | SettingBooleanFlagDef` gives declaration-site guarantees only: the env variant constrains `onPayload: string` and `settingDeleteGuard?: never`; the setting variant allows a `SettingPayload` `onPayload` and a `settingDeleteGuard` of the same type, so a scalar can be guarded and the deep-equal oracle handles any JSON value. A nested `target.type` check does NOT narrow `onPayload` for consumers: `isEnvBooleanFlag(f)` is the narrowing predicate. `suppress-attribution` guards the object `{commit:'',pr:''}` at key `attribution`; `subagent-cache-5m` is the scalar one (key `subagentPromptCacheTtl`, `"5m"`, default ON, right after `prompt-caching-1h`, which it leaves untouched): subagents write 5-minute cache entries while the main session keeps the 1-hour TTL, and a Claude Code that predates the setting ignores the key. Every registry default must be safe to ship unseen, because init sets flags without asking: `code-mode` is off and not recommended. The registry size is pinned by the `toHaveLength` assertion in `tests/flags.test.ts`.
- **Single equality oracle:** `settingValueHoldsManagedShape(flag, value)` is true iff the flag has a `settingDeleteGuard` and the value deep-equals it (`isDeepStrictEqual`); `settingHoldsManagedShape(settingsJson, flagId)` reads `settings.json` and delegates. Its mirror `settingHoldsUserValue` is true when a guarded setting flag's key is present (an explicit `null` counts) with a value that is not the managed shape, and false for malformed JSON, a non-object root, an unknown or unguarded flag or an absent key. `respectUserOwnedSettings(flags, manifestFlags, settingsSnapshot)` (pure) sets such a flag `false` when the manifest does not record it, so the converge pipeline neither writes nor deletes the user's value. `canDeleteSettingKey` (private) is shared by `applyFlags`' neutral branch and `stripFlags`; `resolveExistingAttributionSuppression` (init-seed KB) and the Step 2b fold delegate too.
- **`convergeFlagsIntoSettings(settingsJson, record, {viewModeExplicit, ownedRecord?, explicitOn?})`** is the fold-before-strip pipeline; both `init.ts` and `persistFlagConfig` MUST call it instead of `stripFlags` + `applyFlags`. Steps: (1) fold view-mode via `resolveFinalViewMode`, so an externally set `/focus` survives unless `viewModeExplicit`; (2) fold existing settings values into the record for unclaimed valued (enum/number/string) flags: "claimed" is decided by `ownedRecord` (omitted → the record itself, the `persistFlagConfig` path; `null` → nothing owned, fresh install; the pre-seed manifest flags on the init path); booleans are never folded here; (2b) adopt guarded boolean settings whose pre-strip on-disk value matches the managed shape, only when the record does not already claim the flag (a claimed `false` or `null` still deletes the block), so a template-written attribution block survives first init; (2c, KB-INV-15) `foldOwnEnvPayloads` over guarded env flags; (3) `stripFlags` then `applyFlags` over the folded record; (4) `orderKeysLike` restores the pre-strip key order, top-level and inside `env`: strip-then-apply re-adds every managed key at the end and the deny list merged AFTER the flags appends `permissions`, so without the restore re-init is no longer byte-for-byte stable. Uninstall calls `stripFlags` directly with no record, keeping its full-sweep semantics.
- **Env own-payload guard:** `EnvBooleanFlagDef.deleteOnlyOwnPayload` marks a flag that deletes its env key only when the value is exactly `onPayload` (`canDeleteEnvKey`, the env twin of the settings oracle); the `code-mode` entry (`CLAUDE_CODE_EXPERIMENTAL_CODE_MODE`, `onPayload` `'1'`) is the only user. It is the same prove-you-wrote-it rule as `settingDeleteGuard`, applied to a string env value.
- **Registry adoption of an on-disk key:** the day a settings key that already ships on disk becomes registry-managed, it must be adopted before the strip pass; the presence of `settingDeleteGuard` is the signal and Step 2b the mechanism.
- **Ownership contract:** the guarded deletion is the prove-you-wrote-it contract (only remove a key whose value is the devflow-managed shape). Its corollary — a guard protects deletion, not overwrite — is why enable overwrites a custom attribution while disable preserves one.

## Flags CLI (`src/cli/commands/flags.ts`)

- **`createFlagsCommand()`** is the root Commander for `devflow flags` (a fresh instance per call; `flagsCommand` is the singleton `src/cli.ts` imports). Options: `--list`, `--status`, `--enable <ids>`, `--disable <ids>`, `--set <assignment>` (repeatable), `--unset <ids>`; bare on a TTY launches the TUI, on non-TTY it prints the status table and exits 1. IDs resolve through `findFlag` (unknown IDs error).
- **`readSettingsSafe`** returns `{ok, content}` / `{ok:false, reason}` and never falls back to `{}` on malformed JSON (that would clobber the user's settings); a non-object root is rejected, ENOENT yields `{}`. `loadFlagContext` is the one shared load path for the mutating branches.
- **`persistFlagConfig(claudeDir, devflowDir, settingsContent, newRecord, manifest, {viewModeExplicit, before?, explicitOn?})`** runs `convergeFlagsIntoSettings`, writes `settings.json` (atomically) and `manifest.json` (`features.flags` = the FOLDED record, so adopted values persist) independently, then prints `writeTimeWarnings` for the final state. It returns a discriminated `PersistResult`: `{ok:true}`, `{ok:false, failed:['settings'|'manifest'...]}` or `{ok:false, reason:'no-manifest'}` (an absent manifest is a failure: "Flags saved." with an unrecorded selection is reverted by the next init). Callers print success only on `ok === true`. `applyTuiResult(...)` (exported) derives `viewModeExplicit` from whether the view-mode row changed and returns `'saved' | 'unchanged' | 'refused' | PersistResult` failure.
- **`handleBare` builds the TUI's starting rows** with `buildFlagRows(respectUserOwnedSettings(record, record, settingsContent))`: only flags the record does not yet record can flip, so an unrecorded `subagent-cache-5m` shows OFF when `settings.json` holds the user's own `"1h"` and a Save does not write `"5m"` over it. The settings snapshot is read in `handleBare`, so the reducer and renderer stay pure; `tests/flags-cli.test.ts` drives it with a mocked `runFlagsTui` that captures the rows.
- **Display vocabulary (one definition, every surface via `effectiveDisplay`):** `--enable` / `--disable` confirmations call `formatFlagValue` (`true` → `on`, `false` → `off`); `--set` confirmations do the same for active values and echo literal `unset` for a `null` input at the call site (the user typed that word); `formatStatusRows` (sanitised with `sanitizeCell`) renders not-adopted rows as `not adopted — default: <effective text> applies on next devflow init`; `--list` prints `upstream default: N` for number flags with `upstreamDefault`, else the `defaultValue` string or `none` (never `unset`).

## Code Mode Flag (`src/core/code-mode.ts`)

Code Mode (experimental) lets one step make several tool calls from code; it does not start while the Devflow proxy, `disable-nonessential-traffic`, a custom base URL and similar settings are active, and the flag registry (never the proxy) owns the env key.
- **Predicates:** `isCodeModeOn(record, env)`: an exact own payload in `env` is on, any other value at the key is off (the user's), else the record's `code-mode === true`. `isTrafficOn` is true for a record `true` or any `env` value other than `0` / `false`. `isProxyOn` is true for `proxy.json` enabled, the manifest `proxy` switch, or an `ANTHROPIC_BASE_URL` classified `ours` / `ours-other-port`.
- **Preflight (`checkCodeModeWrite` in `flags.ts`):** reads the signals before any write, computes `turnsOnCodeMode(before, requestedOn)`, and refuses (exit 1, nothing written) on proxy on or a read failure. `--set` takes the LAST assignment of `code-mode` as `requestedOn`; `--unset` and `--disable` pass false. After a successful persist the CLI reads the signals again for warnings; the success line for `code-mode` adds `CODE_MODE_NEW_SESSIONS_SUFFIX`.
- **Status:** `--status` and the non-TTY table add `codeModeBlockers` plus `codeModeStatusNotes` (a user env value: off because settings override; record off over an own payload: the next write removes the setting). `--list` reads with a null `devflowDir`; `devflow proxy` status reads the manifest through `readGateManifest` + `codeModeManifestSignals`.
- **TUI save (`applyTuiResult`):** a row is "edited" when `configuredValue !== originalValue`. An unedited `code-mode` row is recomputed with `respectUserOwnedSettings` over the fresh settings, so a settings edit made while the editor was open is not overwritten; a refused preflight returns `'refused'`.
- **Shared reader (`read-file-bytes.ts`):** `readFileBytes(path, maxBytes)` stats, opens with `O_NONBLOCK` (a pipe swapped in after the stat cannot block), re-stats the handle and reads at most size + 1 bytes. It returns the Buffer or `'absent'` / `'not-directory'` / `'unreadable'` (special file, oversize, grown while reading). The settings `env` reader, `readProxyState` and `readGateManifest` all use it; the settings reader treats invalid UTF-8 and a BOM as unreadable.
- **`heal: false`:** `readManifest(devflowDir, {heal: false})` normalizes in memory and skips the heal write; `loadFlagContext`, `handleStatus` and the non-TTY bare status use it, so a read cannot write the manifest.

## Flags TUI (`src/cli/flags-view/`, `src/cli/tui/`)

An interactive editor launched exclusively by `devflow flags` bare on a TTY (D40: init applies flags non-interactively in every path). It runs in **inline mode**, rendering in place in the scroll buffer.
- **`flags-view/state.ts`** — the pure state machine: `buildFlagRows(record)` (each `FlagRow` embeds its registry `def`, `hint` and `blurb`, so there is no registry reach-back at render time; a row is edited when `configuredValue !== originalValue`), `collectFlagRecord(rows)` (the inverse, via `tuiToRecord`), `reduce(state, key) → {state, done, saved}`, `resizeViewport`, `BUFFER_MAX_LEN`; inline text edit serves enum and string flags. The TUI uses `null` as the "devflow default" stop and `tuiToRecord` maps it back to `neutralValueOf` (`recordToTui` / `tuiToRecord` live in `core/flags.ts`).
- **`flags-view/render.ts`** — frame renderer. Columns at the 80-col reference: PREFIX 2, LABEL 27, DIRTY 2, VALUE 16, BLURB 30 (dim trailing column, omitted when `blurbW === 0`); widths scale with terminal width (`Math.min(1, cols/80)`). `formatValue` delegates to `effectiveDisplay` for null/neutral values (` (default)` appended for number flags); `true` → green `on`, `false` → yellow `off`; a non-boolean active value is `bold` when it deviates from the devflow default.
- **`tui/cells.ts`** — shared ANSI-aware cell helpers: `sanitizeCell` (strips control characters; prevents terminal injection), `padToVisible`, `truncateVisible`.
- **`flags-view/terminal.ts`** — `runFlagsTui` passes `screen: 'inline'` to `runTui` (`D-INLINE`); the intent type is closed so a new `FlagsIntent` member is a compile error.
- **`tui/terminal.ts`** — the generic `runTui<S,A,C>` driver. `RunTuiSpec.screen?: 'alt' | 'inline'` defaults to `'alt'` (agents-view). Inline: the first frame writes lines directly, later frames use `cursorUp(prevLineCount - 1) + \r`, rewrite and `ERASE_BELOW`; on exit it erases the widget so the caller's clack flow continues. `INLINE_MARGIN` lines stay free below the widget (height clamped to `stdout.rows - INLINE_MARGIN`); `cursorUp(n)` returns an empty string for `n <= 0`, so callers need no guard.

## Anti-Patterns

- **KB-AP-1, KB-AP-2** The render sites (TUI `formatValue`, the `--enable` / `--disable` confirmation, the `--status` not-adopted message, `--list`'s `defaultLabel`) all route through `effectiveDisplay`. The compliance gate runs on interactive Recommended; the attribution gate never does, by design (documented in `attribution-prompts.ts`).
- **KB-AP-4** The template merge runs BEFORE the flags pipeline, so a template-written value would be overwritten, or on the off path leave a stale block. A registry-driven test in `tests/post-install-merge.test.ts` enforces the omission.
- **KB-AP-7** Skipping the restore reintroduces the re-init non-idempotency (#388 AC-3).
- **KB-AP-14** The two tables differ in shape, so TypeScript cannot flag drift. The `the init prompt and devflow gates describe the same levels` describe in `tests/gate-level-prompts.test.ts` pins the exact text of `GATE_LEVEL_HINTS`, `GATE_LEVEL_EFFECT` and `GATE_LEVEL_MEANINGS`. The hints are not doc sites of `tests/guards/implement-resolve-level-docs.test.ts`; full effects live in `GATE_LEVEL_EFFECT`, `devflow gates` and the docs.
- **KB-AP-15** `manifest?.features.gateLevel ?? DEFAULT` turns a stored `null` into `standard`, and init would write that over a value every reader folds to `full`, silently lowering the level. So `FeatureSeed.gateLevel` is raw, the promptless path is `cliLevel ?? stored` (the only `??`), and an absent key stays out of the manifest write. The same holds for a rejected manifest's level and `buildHudOnlyManifest`'s `refusedGateLevel`.
- **KB-AP-16** The machine level and the personal level are different keys: the wizard text says "the machine default", and `tests/init-gate-level-e2e.test.ts` pins that init leaves a repository config without `gateLevel` alone and keeps an existing personal key.

## Gotchas

- **`--set flag=unset`** parses to `null` via `parseFlagValueInput`; the `handleSet` confirmation special-cases `null → 'unset'`, the only place `unset` reaches user-facing output.
- **KB-AP-13** A flags TUI test expecting `ENTER_ALT` fails for `runFlagsTui` but passes for agents-view tests; use `screen: 'alt'` when testing alt-screen behaviour.
- **Selective uninstall never strips flags** (`runCleanupPhase` only; uninstall KB), so flag state persists when plugins are removed.
- **KB-INV-12 wiring test is source text:** the `init.ts wiring` describe in `tests/gate-level-prompts.test.ts` regex-matches `init.ts`: one `resolveGateLevelForInit({` call, one `gateDecision = await runGateLevelStepAt(...)` per path and no other assignment beside the `let`, and the `mode,`, `modePromptShown,`, `stored: gateDecision.level,`, `storedOrigin: carriedGate.origin,`, `carriedGateLevel` input and `kept:` lines verbatim. Reformatting fails it by design.
- **Rejected and unreadable manifests (KB-INV-13):** a promptless init over a rejected manifest keeps the raw level and warns; a prompt answer or `--gate-level` replaces it and `--reset` removes it (as `(was full)`), with no warning. Over an unreadable one a promptless init writes no level and warns with the hint (`tests/init-gate-level-e2e.test.ts`).
- **KB-INV-11 `--hud-only` writes early:** it writes before the wizard, so the `--gate-level` parse sits above every write; an invalid value leaves an existing install byte-for-byte unchanged (`tests/init-gate-level-e2e.test.ts`).
- **KB-AP-17 note width:** `@clack/prompts` `note()` pads each row to the longest line, and neither it nor the select hint wraps. `collectGateLevelPromptLengthDefects` (`tests/gate-level-prompts.test.ts`) holds `GATE_LEVEL_HINT_MAX` and `GATE_LEVEL_NOTE_LINE_MAX` for the hint and every note line for every origin in `STORED_GATE_LEVEL_ORIGINS`. Shorten a failing line, never raise a cap.
- **KB-INV-15 silent fold-down:** a record `true` over a user env value (for example an own `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE` of another string) is folded to `false` on any write that does not list the id in `explicitOn`, and is persisted as `false`; only an off-to-on request overwrites the user's value. `tests/write-set-fence.test.ts` pins that a refused `--enable code-mode` writes nothing.
