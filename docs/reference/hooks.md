# Hooks and Background Workers

The hook-driven subsystems: working memory, ambient mode, the curation pipeline, and debug tracing. Hook scripts live in `src/assets/scripts/hooks/`.

**Two roots.** Every hook reads machine-wide state — the manifest and its switches, tracker files, the proxy state, logs — from `$HOME/.devflow`, and nothing relocates it: `DEVFLOW_DIR` is ignored (D-ONE-HOME). Per-project data lives under the repo's own `.devflow`, which the hooks hold in `PROJECT_DEVFLOW_DIR` (the proxy hook names the machine root `MACHINE_DEVFLOW_DIR`).

**Legacy project-local installs (D-LEGACY-LOCAL-NOTICE).** `devflow init --scope local` is retired, but a repository may still hold its `<root>/.claude/settings.json`, whose devflow hooks then run beside the machine-wide ones. `session-start-context` Section 4 recognises one by the exact ownership shape (a command ending in `/scripts/hooks/run-hook <name>` for a hook devflow registers, or a v1 `.sh` hook) and emits one line asking the model to tell the user, once, to run `devflow uninstall --scope local`. It never fires for the machine-wide Claude Code directory, and a `settings.json` with no devflow hook costs a builtin read and no subprocess.

**Compaction resume directive (D-COMPACT-RESUME-DIRECTIVE).** After a compaction nothing tells the model to re-read the devflow command it was running. On a SessionStart whose `source` is `compact`, `session-start-context` Section 5 appends one fixed line of at most 250 ASCII characters (249 today; a `compact-directive-max-chars` ceiling pins it) to `additionalContext`: if a devflow command was running, read `commands/devflow/<name>.md` in `$CLAUDE_CONFIG_DIR` when it is absolute, else `~/.claude`, list the headings, read from the current phase, take the command's input (`COMMAND_INPUT` or `ARGUMENTS`) from the summary and resume after the last finished phase, else ignore. The gate is a positive `compact` case, taken in every project; the string is single-quoted and interpolates nothing; the model, not the hook, decides whether a command was running. `source` is read with the working directory in one subprocess. With neither jq nor node the hook returns before Section 5, so no directive is emitted there. Sections 3 and 4 still gate on `startup` and `clear` only.

**CLAUDE.md import audit (D-CLAUDE-MD-IMPORT-AUDIT, D-AUDIT-STAMP, D-SYSTEMMESSAGE-ENVELOPE).** A CLAUDE.md `@path` import loads its file into every thread at launch. Section 6 audits the Claude directory's `CLAUDE.md` and, in a git project that is not HOME, the project's `CLAUDE.md`, `.claude/CLAUDE.md` and `CLAUDE.local.md`, and names an import over 10,000 bytes or a root whose import chain totals over 40,000 bytes once, in a top-level `systemMessage` that never enters the model's context (`json_session_output "$CONTEXT" "$SYSTEM_MESSAGE"`; a message with no context is `systemMessage` alone, and the one-argument envelope is unchanged). The grammar, bounds (four hops, 64 paths per root, 64 KiB scanned per file, 1 MiB read per run), display gate and stamp format live once, in `claude-md-audit.cjs`, which only reads; the hook runs it, and `devflow init` runs it through `src/core/claude-md-audit.ts`. The stamp `~/.devflow/.claude-md-audit` records the root set, every examined path with an existence flag, and the finding keys already shown. An unchanged start compares the root set and each path (`-e`, `-nt` the stamp) with shell builtins: no fork and no node process. A changed start runs the script once; a machine with no CLAUDE.md anywhere records its stamp with builtins. A finding is recorded only after the output was emitted, a failure shows nothing and records the roots with an error marker (a changed root set retries), and the stamp is written only under an existing `~/.devflow`, through an owner-only temp file renamed into place, never through a link. Two gaps are accepted: a file whose mtime is moved back before the stamp is missed until its next forward change, and a write landing during an audit can be missed the same way. Sections 5 and 6 add no exit path. Uninstall removes the stamp.

## Project Roots, Worktrees and Detached HEAD

**Git projects only (D-HOOKS-GIT-ONLY).** No hook creates `.devflow/` or touches `.gitignore` outside a git repository, or in a repository rooted at HOME (a dotfiles repo, whose `.devflow` is the machine root). `session-start-context` checks this before its `.gitignore` carve-out and its curation sections, and `ensure-devflow-init` checks it for every capture and memory hook, so memory and curation stop together in a non-git directory. The check is `df_is_project_root` in `git-marker`: a `.git` entry at the root itself plus a comparison of physical paths (`cd -P`), because git reports a toplevel with symlinks resolved while `$HOME` keeps the spelling it was given (macOS `/var` → `/private/var`, a symlinked home). It costs no subprocess. The `.git` entry must sit AT the root — a directory, or the file a linked worktree or submodule carries — never merely above it (D-HOOKS-TOPLEVEL-ONLY): when `git rev-parse` fails inside a checkout (dubious ownership, `GIT_CEILING_DIRECTORIES`), `df_resolve_roots` falls back to the raw cwd, which may be a subdirectory, and the gate then refuses it rather than scaffold `.devflow/` there.

**No writes, and no reads into the session, through a symbolic link under `.devflow/` (D-HOOKS-NO-SYMLINK).** A repository can commit a symbolic link anywhere in its own `.devflow/`, and a shell read or write follows one. So the hooks write under `.devflow/`, and read a file there into the session, a backup or a prompt, only where no link sits between the project's root and that file. Otherwise a linked queue or memory folder would carry captured conversation text out of the project, and a linked working memory, backup or decisions file would bring a file from elsewhere on the machine into the session or the memory refresh's prompt with no one choosing to read it. A refused write is skipped and a refused read is treated as an absent file; either is logged once under `~/.devflow/logs/{cwd-slug}/`, and the hook carries on. The check, `df_no_symlink_below` in `git-marker`, uses builtin tests only and never looks at the root or a folder above it, so a project reached through a linked parent such as macOS `/tmp` works as usual. The curation ops that write refuse a linked `.devflow` or `.devflow/curation` the same way and change nothing (D-NO-LINKED-TREE). Someone who deliberately links `.devflow`, or its `memory` or `curation` folder, gets no capture there. The root `.gitignore` is the one file a hook writes outside `.devflow`: when it is a link, `ensure-root-gitignore` follows it one hop at a time, at most 40, and writes the file it leads to only when that file lies inside the project and outside any `.git` folder in it, the project's own or a nested repository's (no part of its path below the project root may be named `.git`, in any letter case); any other link is left untouched and the skip is logged once (D-GITIGNORE-LINK-INSIDE). `devflow init` applies the same rule, and the CLI's own writes and deletes under `.devflow` refuse a linked `.devflow` or folder the same way; so does `devflow uninstall` when it removes a legacy project-local install, deleting and rewriting nothing through a link in the project's `.devflow` or `.claude` and naming each link it skips (D-CLI-NO-SYMLINK).

**Roots come from git, not cwd.** `resolve-project-root`'s `df_resolve_roots` makes one `git rev-parse --path-format=absolute --show-toplevel --git-common-dir` call and accepts exactly two absolute lines; anything else (a git older than 2.31 echoes the flag back) falls back to the toplevel alone. It sets two roots:

| Root | Holds | Value |
|------|-------|-------|
| `DF_ROOT` | Working memory, the `.gitignore` carve-out, feature knowledge bases | This checkout's toplevel |
| `DF_LEDGER_ROOT` | The curation queue and ledger (`.devflow/curation/`) | The main worktree when this is a linked worktree, the main checkout already has `.devflow/`, and the main worktree is not HOME; otherwise `DF_ROOT` |

One ledger per repository (D-LEDGER-MAIN-WORKTREE) keeps ADR/PF numbering continuous: a ledger anchored at a worktree's own toplevel restarted its numbering and collided with main's. The capture hooks append curation turns to the main queue, the Curation directive names the main root, `decisions_load` reads the main index (D-PROMPT-ROOT), and `devflow curation` and the HUD's curation count resolve the same root with the same single git call (`getLedgerRoot` in `src/core/ledger-root.ts`). `knowledge_load` and the knowledge write-back use the checkout's toplevel, because knowledge bases are committed per branch. A worktree that already grew its own ledger keeps it on disk; sessions there stop appending to it. The personal `.devflow/config.json` stays per worktree by decision: a new worktree does not inherit the source checkout's personal settings.

**Detached HEAD (D-DETACHED-HEAD).** A commit checked out without a branch:

| Surface | Behaviour |
|---------|-----------|
| Knowledge commit | Skipped, because the commit would be unreachable once HEAD moves. The Knowledge agent reports `KB_COMMIT: skipped (detached HEAD) — uncommitted: <paths>` and the workflow names those paths to the user |
| Worktree discovery | Detached worktrees stay excluded from `/code-review` and `/resolve` auto-discovery (`devflow:worktree-support`) |
| Memory bootstrap | `pre-compact-memory` bootstraps `WORKING-MEMORY.md` stamped `branch: (detached)`, keyed on the HEAD commit, and the backup records `(detached)`; `background-memory-update` stamps the same label |
| Memory header | `session-start-memory` renders `detached @ <short-sha>` instead of `on unknown` |

## Working Memory

**Working Memory**: A capture/spawn split across always-on hooks in `src/assets/scripts/hooks/`. Toggleable machine-wide via `devflow memory --enable/--disable/--status` or `devflow init --memory/--no-memory` — both write `features.memory` in `~/.devflow/manifest.json` and add/remove the memory hooks through the shared `convergeMemoryHooks` transform. A repository can only narrow that switch, never widen it (D-FEATURES-NARROW-ONLY): `"features":{"memory":false}` in the committed `.devflow/project.json` or in the personal `.devflow/config.json` switches memory off in that checkout; the retired top-level `memory` key decides nothing. `capture-prompt` (UserPromptSubmit, always-on) and `capture-turn` (Stop, always-on) — append the user/assistant turn to `.devflow/memory/.pending-turns.jsonl` via the shared `queue-append` helper (dual-write; see Curation pipeline for the sibling curation queue), which uses mkdir-based locking for queue overflow truncation across concurrent sessions; each queue is gated independently by its switch (`queue_read_gates <manifest> <root>`: the manifest, narrowed by `<root>/.devflow/project.json` and `config.json` `features.*`; a missing manifest or key means on, and only a literal `false` narrows. A repository file that is absent or holds no `false` costs no fork; one that could narrow costs exactly one `node` fork on `resolve-settings.cjs`'s own reader and fold, D-GATES-FAST-PATH); neither ever spawns anything. `memory-worker` (Stop; Claude Code runs one event's hooks in parallel, so it can fire before `capture-turn` has appended the turn — the worker tolerates that, below) — after the 120s throttle (keyed by `.working-memory-last-trigger` mtime), touches the trigger then spawns `background-memory-update` as a detached `nohup` worker, a `claude -p` run on `agents.memory` (default `claude-sonnet-5-5`, high effort; `devflow agents` overrides it). `background-memory-update` (detached worker, not a hook itself) — drains `.pending-turns.jsonl`, calls `claude -p` (prompt on stdin, never argv) with a reconciliation-aware prompt (bounded git evidence since last stamp, reconciliation/provenance sections, strict DONE definition); writes to `WORKING-MEMORY.md.new` (staged file, never the real path directly); then compare-and-swaps: checksums `WORKING-MEMORY.md` before and after the LLM run — if unchanged, renames `.new` → `WORKING-MEMORY.md` (UPDATED) and touches `.last-refresh-ok`; if changed by a concurrent human edit, CONFLICT path keeps the human's version, discards `.new`, leaves `.processing` for retry; if staged file absent or un-stamped, FAIL path leaves `.processing` for session-start-memory crash recovery; holds a 300s-stale worker lock; a queue holding only user rows is left in place with no LLM run, so the next run takes the whole turn once the assistant row lands (D-QUEUE-NO-ORPHAN-DELETE; queue-append caps the file). `session-start-memory` (SessionStart) → injects previous memory with git-reconciled header (3-state: A in-sync / B drifted / C refresh-failing — State C queue depth now counts both `.pending-turns.jsonl` lines and any orphaned `.pending-turns.processing` lines) as `additionalContext` (current working memory only; legacy backup memory is never injected); stamp `<!-- memory-head: <sha> branch: <name> -->` on line 1 drives drift detection; also recovers a stale orphaned `.pending-turns.processing` itself (self-contained cold path, no external helper). PreCompact hook → saves Git state to backup.json without a working-memory snapshot; when WORKING-MEMORY.md is absent, bootstraps it with the line-1 stamp and the five canonical sections in fixed order (requires a 40-hex HEAD sha — an unborn branch skips bootstrap, and a detached HEAD bootstraps with a `branch: (detached)` stamp). Memory sections: `## Now`, `## Progress`, `## Decisions`, `## Context`, `## Session Log`. The background-memory-update worker uses rename-to-claim for queue consumption (atomically renames `.pending-turns.jsonl` → `.pending-turns.processing`). Disabling memory writes `features.memory: false` to the manifest, removes the three memory hooks and drains the current repo's queue; the always-on capture hooks stay registered (shared with curation) and stop appending to the memory queue. `removeMemoryHooks` (used by `devflow init --no-memory`) also removes legacy hooks from prior architectures. Use `devflow memory --clear` to clean up pending queue files across projects. The worker's write is limited to its staged file: the `claude -p` run loads only the user's settings plus two rules, an Edit allow rule for `WORKING-MEMORY.md.new` and an Edit deny rule for every path under it, and a permission mode that denies every call no rule allows. Allow rules in the user's own settings also apply to the run. A folder or a link at the staged path is removed before the run and after it, by one guarded delete of exactly that path (only inside the project's `.devflow/memory`, never through a link, a folder with a long listing is left); a run that finds one after it ends as `failed`, with the reason in the log. It needs the minimum Claude Code version that `devflow init` names at its working-memory step; on an older Claude Code the worker does not run, keeps the queue and writes one log line. If neither `jq` nor `node` is on PATH, the worker logs `SKIP: neither jq nor node on PATH; the queue is kept for the next run; no LLM run`, exits 0 and keeps the queue and any leftover batch. If the JSON parser exits non-zero on the queue or on the batch, the worker also keeps them for the next run and runs no LLM. Both cases end with `result=skip`. A queue line that holds no readable turn is skipped alone, and the worker logs `Skipped <n> queue line(s) that hold no readable turn`. Each run ends with one line in `.background-memory-update.log` under `~/.devflow/logs/`, in the folder for the session that ran the worker (`<session-directory-slug>`), `Run: cli=<version|unknown> argv=<lean|legacy|none> result=<updated|conflict|failed|skip|below-floor> denials=<count|unknown|n/a> removed=<none|dir|link>` (a below-floor line adds `floor=<version>`); it holds keywords and digits only, never turn or prompt text. The same log holds one `Result:` line for the run: the result's subtype, its `is_error` flag, the turn count, the denial count and, when the result carries one, `api_status=<digits>`. The CLI's stderr is appended to the worker log. The JSON result is reduced to that one `Result:` line of shape-checked fields, so the result's own text is not logged. The worker writes the `Result:` line only when claude started and the worker holds a result file; a file with no readable result gives `Result: not reported (empty|unparseable|no parser)`. A project under a `.git` folder gets no working-memory update: the worker skips it, logs the reason and raises one `path` notice at session start. Known limit: a project path that holds any of `* ? [ ] \ " { }` or a control character gets no working-memory update either, because the permission rule carries the path without quoting; the worker skips it, logs the reason and raises one `path` notice at session start. Parentheses and spaces in the path are carried as they are. When the worker left a notice (`path` or `denied`), `session-start-memory` also returns that notice once as `systemMessage`, beside the context and never in it. It shows even when no working memory exists. A project under a `.claude` folder, such as a checkout in `.claude/worktrees`, is updated like any other. Zero-ceremony context preservation.

**A paused memory folder.** While git tracks a file in the memory folder (`.devflow/memory/`) of a checkout, or a `.git` entry stands there and git does not answer, memory is paused for that checkout, and no memory hook reads or writes in it. The check asks at the checkout's toplevel, not at the ledger root. `unknown` pauses like `tracked`. `capture-prompt`, `capture-turn` and `capture-question` append no row to the memory queue: the gate in `queue-append` logs `Queue skipped: the memory area is paused ...; nothing written`. `session-start-memory` asks in `node` mode, so a git that hangs is cut. A pause makes it move no batch and read no working memory, no refresh warning, no queue and no worker notice. It logs `Memory paused: ...` and, on `startup`, `resume` and `clear` only, sends the fixed memory notice as a `systemMessage` with no context. A compaction sends nothing. `pre-compact-memory` asks in `node` mode too, and a pause makes it create no folder, write no backup and bootstrap no working memory. `memory-worker` (Stop) asks in `git` mode after the throttle, and a pause stamps no trigger and spawns no worker. `background-memory-update` asks git for itself at three points: on the path of an unresolved root, before it leaves a notice; after it re-checks the switch; and after the `claude -p` run. A pause at the second point ends the run as `skip` with the log line `SKIP: the memory area is paused ...`. A pause at the third point ends it as `skip` too, and the batch stays in `.processing`: nothing is swapped, no stamp is written and no denied marker is left. The worker holds its call to `DEVFLOW_BG_AREA_PROBE_SECS` seconds (default 5, from 1 to 60). A call that is cut off reads `unknown`, and the area stays paused. Of the helpers in `memory-permission`, only `memory_notice_write` and `memory_denied_seen` check the memory area, and they leave no notice and no marker unless the area is free. `memory_notice_read` and `memory_notice_clear` check nothing themselves. Their callers ask the area first and stop when it is paused, so a paused checkout has no notice read and no notice cleared. Known limits: `capture-prompt`, `capture-question` and the Stop hooks (`capture-turn` and `memory-worker`) ask in `git` mode, which has no time bound of its own, so only the hook timeout of Claude Code cuts a hung git there. `ensure-devflow-init` runs before the check of the Stop hook, so a paused checkout can still get empty scaffold folders from it. With no `node` on PATH, `session-start-memory` and `pre-compact-memory` ask in `git` mode with no time bound. `devflow memory --clear`, `devflow memory --disable` and `devflow init --no-memory` leave the queue of a paused project in place and print the memory notice.

## Ambient Mode

**Ambient Mode**: Two-hook orchestrator system (git repos only) controlled by a single toggle (`devflow ambient --enable/--disable/--status` or `devflow init`). **`session-start-orchestrator`** (SessionStart, presence-gated) — injects the orchestrator charter (~700 tokens) as `additionalContext` at every session start (startup, `/clear`, resume, compact). The charter establishes the main session as an orchestrator: delegate work to roster agents chosen by kind of work (Explore, Skim, Code, Validate, Git, Design, Research, Review, Triage) — never pinning a model, so each agent runs on its configured model and effort — or full devflow workflow skills; work that fits no row goes to the closest roster agent, never general-purpose; keep judgment work mainline, plus one bounded inline exception (a single git, gh or script command whose output stays under about 40 lines, never a diff, log or test run). Direct delegations ask the agent for a final report of at most about 1,500 tokens. Also carries a plan-handoff fallback bullet that invokes `devflow:implement` with no arguments, because the plan is already in the conversation (SessionStart provably fires even when UserPromptSubmit does not). **`preamble`** (UserPromptSubmit, presence-gated) — three behaviors: (1) if prompt begins `Implement the following plan:` (Claude Code's native plan-mode handoff prefix), injects a directive to immediately invoke `devflow:implement` with no arguments; (2) slash commands (`/...`) are silenced; (3) all other prompts get a 2-line orchestrator reminder. Both hooks are silent outside git repos. Any legacy `commands.md` rule or `session-start-classification` hook from prior installs is auto-removed on every `devflow ambient --enable/--disable` or `devflow init`.

## Curation Pipeline

**Curation pipeline** (directive-spawned background Curate agent — scripts capture and trigger only): `capture-prompt`/`capture-turn`/`capture-question` (all always-on) append every user turn, assistant turn, and answered `AskUserQuestion` to `.devflow/curation/.pending-turns.jsonl`, gated by `features.curation` in `~/.devflow/manifest.json`, which the checkout's `.devflow/project.json` or `.devflow/config.json` can narrow with `"features":{"curation":false}` but never widen (D-FEATURES-NARROW-ONLY; a missing manifest or key means on). Every write of the manifest keeps the old key `features.learning` equal to `features.curation`, so a downgraded 3.7 install reads the same value. A reader treats two disagreeing keys as off, and a repository file narrows under either key. The first `devflow` command that loads the whole manifest (for example `devflow init` or `devflow flags --status`) heals it. The heal writes both keys. The `--status` commands of curation, memory, knowledge and gates write nothing. The repository files are read at the checkout's toplevel (`DF_ROOT`), not the ledger root, so a linked worktree whose branch narrows curation stops feeding the shared ledger while other worktrees keep capturing. `session-start-context` Sections 1–2 read the same gate via `queue_read_gates`. The queue and ledger live at the main worktree's root in a linked worktree (see Project Roots above). `session-start-context` Section 1 injects each rendered file's TL;DR count under `--- PROJECT DECISIONS (TL;DR) ---`, then `Index: <ledger root>/.devflow/curation/index.md` when the ledger root passes the directive's shape gate (below) and the index is present, non-empty and not `(none)`; a one-line rule after the Index line tells the main model to read that index once and, on direct delegations, to pass each agent that takes DECISIONS_CONTEXT only the index lines that touch its work, verbatim, behind a `(slice: N of M entries — full index: <path>)` line and with the index footer (the rule lives here, not in the orchestrator charter, so it follows the curation switch and reaches sessions with ambient off). `session-start-context` Section 2 (SessionStart, always-on) — when the curation queue is non-empty, or a crashed run left a `.pending-turns.processing` batch older than 900s, it resolves the model in four layers and the first that supplies one decides (a valid project `.devflow/curation/curation.json` `model` → an `agents.curate.model` entry in `~/.devflow/agent-models.json` (else an older `agents.learning.model` entry), the `devflow agents` Curate mapping → a valid global `~/.devflow/curation.json` → none) and emits a `--- CURATION MAINTENANCE ---` directive instructing the main model to **silently** spawn `Agent(subagent_type="Curate", model=<resolved>, run_in_background: true)` **(never narrated in user-visible text)**, with no `model=` when the mapping or no layer supplies one, so the installed Curate frontmatter decides; a fresh `.processing` suppresses the directive (a live agent owns the batch); queue emptiness is the natural gate, so there is no throttle. The check is advisory and decides only whether to spawn: the claim itself is taken under the curation lock by the `claim-queue` op, which applies the same 900s threshold (D-OWNED-CLAIM), so a spawn that loses a race exits on `busy`. The directive embeds the ledger root only when it matches `^[A-Za-z0-9/._+-]+$` (`+` covers Claude Code's `feat+x` worktree names); any other root with pending work gets a fixed `--- CURATION PAUSED ---` notice that embeds no path, so a paused queue is visible rather than silent.

**The ledger folder move** (3.8: `.devflow/learning/` became `.devflow/curation/`). The shell shim `curation-move` (sourced by `session-start-context`, `ensure-devflow-init` and `queue-append`) and `devflow init` do the same move before any hook creates a folder. Both call `moveLedger` in `hooks/lib/curation-move.cjs`: the shim through the `move-ledger` op of `json-helper.cjs`, and init in process through the `src/core/curation-move.ts` seam. The move runs whether or not the curation switch is on. In the common case it is one rename of the old folder. The shim probes the old folder first, so a project that has no old folder costs no fork. It refuses, with one log line and nothing renamed, when a link sits on the path to the ledger root, or when a private (`.merging-`), swept (`.swept-`) or overflow (`.overflow-`) queue file sits directly in the old folder. A refusal or a failed move leaves a marker under `~/.devflow/logs/`, and the shim does not try that project again until the next session start. The HUD reads this marker. The move also skips a project, and changes nothing in it, when git tracks any entry under `.devflow/learning/`, `.devflow/curation/` or a backup folder, or an entry named `.devflow` itself, or when a `.git` entry stands and git does not answer. The check runs right after the link checks and before the move takes a lock (`hooks/lib/tracked-areas.cjs`): one bounded `git ls-files` call, and no call at a root with no `.git` entry. The backup sweep asks the same check. The op prints `skipped tracked` or `skipped unknown`. After `skipped unknown` it prints a `cause <word>` line, with one fixed word from a closed list (for example `git-not-found` or `git-timed-out`), and the shim puts that word in its log line. The shim writes a `.tracked` or `.unknown` marker under `~/.devflow/logs/`, never inside the project. The HUD reads these markers too, and `session-start-context` (Section 4b) turns the same answer into the curation pause notice, a systemMessage for the user on a session that starts, resumes or is cleared, while curation is on. A busy marker is a separate file, and the HUD does not show it. The move takes a lock at `~/.devflow/.curation-move-<16 hex>.lock`, outside both folders, and never waits for it: a hook that finds the lock held leaves the data in the old folder, and the next event moves it. A lock older than 60 seconds counts as stale. A fresh queue claim in either folder holds the move too, for up to 15 minutes. Then the shim writes a busy marker under `~/.devflow/logs/` and forks nothing for that project until the next session start. A hook never fails and never drops a row on account of the move. A shim file that is missing is no failure either: the hook skips the move and logs the steps that need the folder names. `queue-append` then writes no row, `ensure-devflow-init` makes no ledger folder, and `session-start-context` skips its curation sections.

When a project already has both folders, one rule decides which stays. If `.devflow/curation/` has a non-empty log, it wins and the old folder becomes the backup, `.devflow/learning.backup-<stamp>-<8 hex>`. If not, the old ledger set moves in and the rest of the old folder becomes the backup. Ledgers are never merged into each other. Pending queue rows move into the winner's queue, by unique private files that are marked swept and never deleted, and only while the queue stays within its 100-line merge cap, the number of lines the capture trim keeps. The rest go to overflow files in the backup. A later `devflow init` merges them as room appears, and `devflow curation --status` counts them as pending rows in the backup. No devflow command deletes a backup, except `devflow uninstall`. Uninstall removes the backups of the project at the git root of the current directory, with that project's data, after you confirm. `devflow curation --reset` and `devflow curation --clear` leave the backup in place.

Until a project moves, the CLI and the HUD do not read the old folder. `--status`, `--list`, `--show` and the HUD print a pointer (`Curation: run devflow init, or open Claude Code in this project after it`) or, when the move was refused or failed, `Curation: move refused, see the hook log`. When the move was skipped, the HUD prints one short line, and `--status`, `--list` and `--show` print the whole notice: devflow did not move the data, why, and, when git tracks files, what to run (`git ls-files .devflow`, then `git rm --cached <file>`, in the checkout that holds the folders). When git did not answer, the notice says that the move runs again at the next session start or the next init. The HUD and these three commands show the skip also when both folders exist: the HUD puts it after the counts, `--status` before the counts, `--list` before the listing and `--show` on stderr. The pause check (next paragraph) comes first. While git tracks files in a curation data folder, or does not answer, `--status` prints the pause notice and no counts, `--list` and `--show` print it and exit 1, and, where the new ledger file exists, the HUD shows no counts and no skip line. The skip notice shows only after git answers that nothing is tracked and before the move runs again at the next session start. The writing subcommands ask the pause check first and refuse with the pause notice while the pause lasts. After that, they move the folder, or refuse, and a skipped move writes nothing and exits 1. They print the skip notice only when git's answer changes between the two checks.

**A paused curation folder.** While git tracks a file in a curation data folder at the ledger root (the curation folder, the old ledger folder or a backup folder, with the pathspecs of the move check), or a `.git` entry stands and git does not answer, curation is paused for the project, and no hook or command reads or writes a file in these folders. `unknown` pauses like `tracked`. `capture-prompt`, `capture-turn` and `capture-question` ask in `git` mode before they build a row, with one call for both queues when the two queues share a root. A pause appends no row and logs `Queue skipped: the curation area is paused ...; nothing written`. `session-start-context` runs the check after the move step when curation is on. It reuses the answer of a move that skipped, and otherwise asks once in `node` mode, so a git that hangs is cut. A pause makes it read no curation file, create no curation folder and inject no decisions index, no TL;DR counts and no `--- CURATION MAINTENANCE ---` directive, and it logs `Curation paused: ...`. On `startup`, `resume` and `clear` it sends the fixed notice as a `systemMessage` (`AREA_PAUSE_NOTICE` in `src/core/area-pause-notice.ts`). The notice holds no path, count or git output. It says what is paused and why. When git tracks files, it says to run `git ls-files .devflow` and `git rm --cached <file>` in the main checkout. When git did not answer, it says that the check runs again at the next session start. A compaction sends nothing. While curation is off, session start shows no curation text, and `devflow init` tells the user about a skipped move. Every `json-helper.cjs` op that reads or writes the ledger, the queue or the curation lock, and `render-decisions`, refuse a paused folder with a `tracked` error and write nothing, so a Curate agent that is still spawned stops at its first op. The generic op `tracked-area <curation|memory|both> <root>` prints `tracked`, `untracked` or `unknown`, then a `cause <word>` line for `unknown`. It exits 0 for any answer and asks git once for each area and root in a process. The pause leaves no marker, so each event asks again. `devflow curation` prints the same notice for a paused folder (see the CLI reference).

The **Curate agent** (`src/assets/agents/curate.md`, whose frontmatter sets its model and effort) preloads no skill, keeps the project CLAUDE.md in its context (its Encoded check reads the rules there) and has the tools Read, Bash, Glob and Grep and no Write or Edit: it reads the claimed turns with Read, and reads and writes the curation data only through the `json-helper.cjs` ops run from the ledger root, each taking any text it needs as one JSON object on stdin through a quoted heredoc, and each writer taking the curation lock itself (the ops, the data files and their rules: Project Knowledge in `docs/reference/file-organization.md`). Step 0 runs `claim-queue`: `claimed <token>` (or `claimed <token> takeover`, a batch whose previous run went stale) keeps the token, `busy` exits silently, `none` reports no pending work. Every curation op refreshes the claim's mtime; between ops the agent runs `touch -c` on the claim at the boundary between its two parts and after each maintained entry, and stops without further writes once the claim or the curation directory has vanished. **Capture**: it runs `list` once and `show` on candidates, then reinforces or rewrites the observation that already states a lesson (`put-observation --reinforce|--update`, the whole content every time), restores a retired entry whose lesson came back (`restore-anchor`, then `--update`) rather than minting a new one, or stores a new observation (`--create`); it promotes an observation with `assign-anchor <decision|pitfall> <obs_id>` once it recurs or is clearly significant, and checks any status change the turns report at the verify ref (`git show <ref>:<path>`) before acting on it. **Maintenance**: `rotate-observations`, then one `claim-due`, whose batch is the only bound on the run's maintenance; `due none` ends the part, and otherwise the agent reads `references/curate/maintain.md` of the `agent-references` skill by explicit path and, for each due entry, runs `show` and takes exactly one action, the first rung that fits — Encoded (`retire-anchor … Encoded` with a path and a quote checked at the verify ref), no longer true (a rewrite, or Retired), a duplicate (absorbed into the survivor, then Superseded by it), a one-off (Retired), else Keep (a v1, wrong or vague entry is rewritten with `put-observation --update`) — keeping it when unsure, and ends the part with one `refresh-anchor <anchor>… --verified` of every kept v2 entry. No thresholds or confidence formulas decide any of this: the LLM judges what warrants an entry. The agent's FINAL act is `release-claim <token>` (`released`; `not-owner` or `gone` is noted), and it ends with a 1–3 line summary — native background-task visibility, no status files.

Global tuning config: `~/.devflow/curation.json`, which a `devflow agents` Curate mapping outranks for the model. Project tuning config: `.devflow/curation/curation.json` (`model` and `debug` only — no daily-run cap or throttle), which outranks the mapping. `devflow curation --disable` writes `features.curation: false` to the manifest (every project) and drains the current repo's `.pending-turns.jsonl`, `.pending-turns.processing` and `.pending-turns.owner` in each ledger folder that exists, and the pending-row files of the backups (a mid-run agent whose claim vanishes stops without further writes — the desired outcome of disabling; mirrors memory.ts's disable-drain). The drain asks the tracked-areas check first. When git tracks any entry under `.devflow/learning/`, `.devflow/curation/` or a backup folder, or does not answer, it deletes no queue file and prints the fixed notice once; the switch stays recorded. Toggleable machine-wide via `devflow curation --enable/--disable/--status` or `devflow init --curation/--no-curation` — both write the same manifest value under both keys, and both converge the installed commands, agents and the `devflow:apply-decisions` skill to it (the curation-off variants, see file-organization.md). The other subcommands load the package's own copy of the curation store (D-LEARNING-STORE-SEAM): `--status` adds the entry counts (active by type, inactive by status, active entries still in the v1 format, observations) and warns of skipped malformed lines; `--list` prints the `list` op's listing; `--show <id>` prints the `show` op's JSON for an entry or observation, with control and bidirectional characters escaped for the terminal; `--restore <id>` makes an inactive entry active again; `--configure` writes the tuning config; `--clear` drops only the observations no entry uses (D-CLEAR-UNREFERENCED) — a malformed ledger line writes nothing and exits 1 — and drains the queue only after the clear succeeded, and only when the tracked-areas check answers `untracked` (otherwise it prints the fixed notice and deletes no queue file); `--reset` removes `.devflow/curation/`, and when there is none prints `No curation data to reset.`, creates nothing and exits 0. `--restore`, `--clear` and `--reset` wait at most 5 s for the curation lock, and when it stays busy they change nothing and exit 1. `--status`, `--list` and `--show` write nothing. `--status`, `--list`, `--show`, `--restore`, `--configure`, `--clear`, `--reset`, the `--disable` drain and the `init --no-curation` drain resolve the ledger root by the `DF_LEDGER_ROOT` rule (`getLedgerRoot`), so in a linked worktree they act on the main checkout's ledger, the one the hooks write; outside a git project `--list` and `--show` read the current directory.

## Debug Tracing

Debug logs stored at `~/.devflow/logs/{project-slug}/`.

**Log folder cap (D-LOG-DIR-CAP).** Every hook logs under `~/.devflow/logs/{cwd-slug}/`, one folder per working directory. `devflow init` keeps the 200 (`MAX_HOOK_LOG_DIRS`) most recently written folders and removes the rest, oldest first. It reads at most 100,000 folders a run and removes every one of them beyond the cap, so one init clears the backlog it read (about 2.2 s per 10,000 removals); only a larger backlog waits for the next init. `log-paths`' `devflow_log_dir` prunes too, but only when it creates a new folder — at most 50 per call, bash 3.2, no node — so a machine that never re-inits stays bounded and the common path (the folder exists) costs nothing; the debug trace takes its per-project folder from the same function. Files at the logs root (`proxy.log`) and symbolic links are never counted or removed.

**Debug Tracing**: Single global toggle covering all hooks. Enabled via `devflow debug --enable/--disable/--status` CLI or by setting `DEVFLOW_HOOK_DEBUG=1` in `~/.claude/settings.json` env block (survives reinstalls). All hooks share the `src/assets/scripts/hooks/debug-trace` helper script (sourced via `hook-bootstrap`) so tracing behavior is consistent and updated in one place. Two-phase logging: pre-CWD traces go to global `~/.devflow/logs/.hook-debug.log`; post-CWD traces go to per-project `~/.devflow/logs/{project-slug}/.hook-debug.log`. A 5MB size guard prevents unbounded growth.
