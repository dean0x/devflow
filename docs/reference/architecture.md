# Architecture

These are the descriptions behind the rules in the CLAUDE.md Architecture Overview. CLAUDE.md holds the binding rules. This file explains them.

Registry-driven CLI tool with 21 plugins (12 core + 9 optional). Plugins are entries in DEVFLOW_PLUGINS in `src/core/plugins.ts` — each entry declares its `commands`, `agents`, `skills`, and `rules` arrays. All assets live once in `src/assets/`; most install directly, and `.mds` sources compile via `npm run build:mds` — command hosts to `dist/commands/`, agent generator hosts to `dist/agents/`, and reference modules in `src/assets/mds/` to `dist/skills/git/references/`.

**LLM-vs-plumbing principle**: The LLM does all detection, semantic matching, materialization, and curation — it reads the curation data through the `list`/`show` ops and writes it through `put-observation` and the other ops, never by editing the files. Deterministic code is plumbing only: hooks, locks, throttles, file I/O, the curation ops' input validation, `assign-anchor` numbering, re-projection and status changes, `claim-due` due selection, the queue claim, `render-decisions` rendering (decisions.md + pitfalls.md + index.md), and `rotate-observations` archival. No detection or judgment logic lives in shell or TypeScript. Ledger IDs are machine-local, so committed and posted text states a decision in words, never by its ID.

**Runtime data**: one install per machine, no install scope: `~/.devflow` is the machine root (`DEVFLOW_DIR` is ignored) and the Claude Code directory is `$CLAUDE_CONFIG_DIR` (absolute) else `~/.claude`. `init --scope local` exits 1; `uninstall --scope local` removes a legacy repo-local install without touching HOME. A repo's `.devflow/` is local by default except `features/` (`index.md` + `{slug}/KNOWLEDGE.md`), `conventions.md`, `policy.json` and `project.json`, which are git-tracked. `conventions.md` is the naming-conventions authority, learned only when `APPLY_CONVENTIONS` is `true`; re-learn it by deleting the file. `project.json` holds the team's settings (evidence, compliance, tracker, a `reviewPublication` ceiling, `features` switches) and `policy.json` is retired, kept tracked only so a committed copy still holds its repo at `required`: the team commits them, devflow never writes them. `.devflow/config.json` holds personal per-repo facts only (`reviewPublication`, the narrow-only `tracker` override, `features`, and `gateLevel`, which may raise or lower the machine's gate level and is not a switch); a copy git tracks is not personal and is ignored as absent, with a warning to `git rm --cached` it (D-PERSONAL-UNTRACKED). Memory, curation and knowledge are machine switches in `~/.devflow/manifest.json` that either repo file can only narrow (D-FEATURES-NARROW-ONLY). The gate level is a machine default, `features.gateLevel` in the same manifest (`devflow gates --set`, or `devflow init`: a wizard step and `--gate-level <level>`), that a personal `gateLevel` overrides in either direction; a `gateLevel` in `project.json` is ignored, and no command writes the personal key. `features.behavior` is the opt-in switch: off unless set, it installs the feature-owned `behavior` rule (like compliance, in no plugin's `rules`) while rules are on, and `devflow init --[no-]behavior` or `devflow behavior --enable/--disable` sets it (D-BEHAVIOR-OPT-IN). Prompts never read `project.json` or `config.json`: they take the one `resolve-settings.cjs` line through `_partials/_settings.mds`, and `tests/guards/no-config-read.test.ts` holds them to it. `~/.devflow/tracker/{provider}.md` (per-provider conventions) is user content, kept on uninstall.

**Curation data move**: the curation feature was called learning before 3.8, so its folder `.devflow/learning/` became `.devflow/curation/` and its tuning file `learning.json` became `curation.json`. One contract moves them. `devflow init` (`curation-move-step.ts`) and the `curation-move` shell shim at session start both run it. Both call `moveLedger` in `hooks/lib/curation-move.cjs`: the shim through the `move-ledger` op of `json-helper.cjs`, and init in process through the `src/core/curation-move.ts` seam. So the two paths cannot differ. The ledger root decides the folder (D-LEDGER-MAIN-WORKTREE), and a project that no run reaches keeps its old folder. The rules: (1) the move waits for no lock; it takes a move lock at `~/.devflow/.curation-move-<16 hex>.lock`, outside both folders and stale after 60 s, and a busy move leaves the data in the old folder for the next event (a fresh queue claim makes the move busy with the reason `claim`, and then the shim writes a busy marker and forks no more until the next session start); (2) it refuses and changes nothing when a link sits on the path to the ledger root or is the source or the target of an entry; right after those link checks, and before it locks, reads or renames anything, it skips the project and changes nothing when git tracks any entry under `.devflow/learning/`, `.devflow/curation/` or a backup folder (a staged entry counts, and so does an index entry named `.devflow`), with the reason `tracked`, or when a `.git` entry stands and git does not answer, with the reason `unknown` and one fixed cause word; the check is `hooks/lib/tracked-areas.cjs`, a leaf that requires neither the store nor the move: one bounded `git ls-files` call over fixed pathspecs, which makes no call at a root with no `.git` entry; the backup sweep asks the same check, and so do the queue drains of `devflow curation --disable`, `devflow curation --clear` and an init that runs with curation off, which delete no queue file when the answer is not `untracked`; the shim writes a `.tracked` or `.unknown` marker under `~/.devflow/logs/`, outside both folders, and the next session start looks again; a private (`.merging-`), swept (`.swept-`) or overflow (`.overflow-`) queue file that sits directly in the old folder refuses the move in the whole-folder case, which runs while the move holds its locks; (3) it never merges one ledger into another: when both folders exist, if `.devflow/curation/` has a non-empty log, it wins and the old folder becomes the backup `.devflow/learning.backup-<stamp>-<8 hex>`; if not, the old ledger set moves in and the rest of the old folder becomes the backup; (4) queue rows move by append, never above the 100-line merge cap (the number of lines a capture trim keeps), and the rest go to overflow files in the backup; a source file is marked swept and never deleted; (5) a crash leaves a journal at `~/.devflow/.curation-move-<16 hex>.journal`, beside the move lock and never in the repository, a rerun completes the set in a fixed order, a journal records the identity of the old folder it was planned for and a journal of an old folder that was since replaced is dropped, not replayed, a store write that meets the journal answers busy, and a file named `.curation-move.journal` in the old folder is never read; (6) a hook exits 0 and drops no row; (7) nothing reads the old folder as a ledger, and the move only moves its files: the CLI and the HUD never read the old folder and print a pointer, a refused line after a refusal or a failed move, or a skipped line after a skip, instead, all from `src/core/curation-move-notice.ts`, which also names the markers' paths, and the fixed notice of a skip is `src/core/curation-move-skip.ts` (init, `devflow curation` and the session start context show it); when both folders exist and a skip marker stands, the HUD and `devflow curation --status`, `--list` and `--show` show the skipped line beside what they read; (8) no devflow command deletes a backup, except `devflow uninstall`, which removes the backups of the project at the git root of the current directory, with that project's data, after you confirm; `devflow curation --reset` and `devflow curation --clear` leave it in place, a disable (`devflow curation --disable`, or every init that runs with curation off) removes only the pending-row files in each backup (the files that status counts, within the sweep's limits) and nothing else in it, and a link in the way refuses that drain whole; every drain (a disable, an init that runs with curation off, and `devflow curation --clear`) deletes no queue file in a live folder, an old folder or a backup when git tracks any entry under a data folder or a backup folder or does not answer, and each of these three drains prints the fixed notice once (an init that has just printed it in its `Ledger move skipped for <root>` line adds only the sentence `The curation queue was not drained.`); `devflow curation --status` counts its pending rows so the owner knows when to delete it, with one line for each of the first 50 backups, one total line for the 51st to the 500th (the folders it reads) and one line for those past the 500th, which it does not read.

**Curation switch**: the machine switch is kept in `~/.devflow/manifest.json` under two keys, `features.curation` and its pre-rename copy `features.learning`. Every write sets both to the same value, so a downgrade reads the same answer. A `false` in either key wins, and a disagreement never reads as on. The first `devflow` command that loads the whole manifest (for example `devflow init` or `devflow flags --status`) heals it. The heal rewrites the pair once, when it finds the pair unequal or incomplete. The `--status` commands of curation, memory, knowledge and gates write nothing. The heal and the toggles of the `memory`, `curation`, `knowledge` and `behavior` switches (`--enable` and `--disable`) run under a lock directory, `~/.devflow/manifest.json.lock`, stale after 5 s. A toggle waits for it at most 7 s. The heal never waits: it skips when the lock is held, because the next read heals, and under the lock it writes only when the file still holds the bytes it parsed. Each holder checks, just before its write, that the lock directory still holds the random token it wrote inside it at creation. If it is not, the heal skips, and the toggle takes the lock again at most three times within the same 7 s and then writes without it. A `--disable` that lands after the heal parsed the file is therefore never overwritten by the heal. The lock covers only these writers. The other manifest writers take no lock: the `hud`, `security`, `proxy` and `tracker` toggles, the `flags` and `rules` writes, the gate level writer and init. Issue #587 tracks them. The repo layer follows D-FEATURES-NARROW-ONLY: `features.curation` and `features.learning` in `project.json` or `config.json` are parsed each on its own, and the layer is off when any of them is a literal `false`. A non-boolean value is ignored for its own key only. The oldest key, `decisions`, counts on the machine only when no current key is a boolean, and in a repo file it decides nothing. The four readers (`feature-switch.ts`, `resolve-settings.cjs`, `project-config.cjs` and `queue-append`) agree on every row of one table. A person's `config.json` under the old key still narrows, and no write path rewrites it. The settings line field is `CURATION=`.

**Tracked data folders**: when git tracks a file in a data folder of curation or memory, or a `.git` entry stands and git does not answer, devflow reads and writes no file in that area's folders. Curation covers the curation folder, the old ledger folder and the backup folders at the ledger root. Memory covers `.devflow/memory/` of the checkout. Each area is judged on its own at each event by `hooks/lib/tracked-areas.cjs`: one bounded `git ls-files` call over fixed case-insensitive pathspecs, in which a staged entry counts and so does an index entry named `.devflow`. A root with no `.git` entry makes no call. A call that fails or is cut off reads `unknown`, and `unknown` pauses an area like `tracked`. The TypeScript seam `src/core/tracked-areas.ts` and the shell twin in `queue-append` give the answers of the leaf, and a parity test holds the three together. While an area is paused: the settings line reads `CURATION=off` or `MEMORY=off`; the capture hooks append no row to its queue; the curation store ops and `render-decisions` refuse with a `tracked` error and write nothing; the memory hooks and the memory worker read and write nothing, and the worker ends a run in progress without a swap or a stamp; the session start hooks inject nothing from the area and send one fixed notice (`src/core/area-pause-notice.ts`, with no path, count or git output) on `startup`, `resume` and `clear`; `devflow curation` and `devflow memory` print the same notice, change nothing and skip every queue drain; the HUD shows no curation counts; and `devflow uninstall` keeps the folder. The pause leaves no marker. Each event asks git again, so untracking the files ends the pause at the next event.

**Feature Knowledge Bases**: `.devflow/features/index.md` + every `{slug}/KNOWLEDGE.md` are git-tracked and shared through the root `.gitignore` carve-out (written byte-identically by `ensure-root-gitignore` / `ensureDevflowGitignore`). After writing, the **Knowledge agent commits those two paths to the current worktree branch itself** (scoped `commit --only` pathspec, never `git add -A`, **never push, never force**, no commit script). A user opts back out by re-adding `.devflow/features/` to their own `.gitignore`. The settings line's `KNOWLEDGE` (the machine switch — `devflow init --[no-]knowledge` or `devflow knowledge --enable/--disable` — narrowed by either repo file) gates write-back only; load is ungated, and explore/debug do NOT load up-front (intentional asymmetry). Freshness = write-through + verify-on-read (NO git-staleness, NO SessionEnd eval, NO Curation task).

**Rules**: plugin-scoped flat `.md` files in `src/assets/rules/`, installed to `~/.claude/rules/devflow/` for the selected plugins only (the compliance rule is feature-owned). Shadow overrides: `~/.devflow/rules/{name}.md`. `paths: []` YAML frontmatter must remain — it signals Claude Code to apply the rule globally.

**Selection-scoped Skill Installation**: skills install for the plugins you selected plus every skill those plugins declare in `requires:`, as `~/.claude/skills/devflow:{name}/`. Shadow overrides live at `~/.devflow/skills/{name}/` (unprefixed); a shadow whose skill is outside the selection is dormant — kept in `~/.devflow/skills/`, never installed, never deleted. Deselecting a plugin removes only the skills no remaining selected plugin owns or requires. Exception: the `compliance` skill is feature-owned (not plugin-scoped).

**Compliance**: feature-owned regulatory review (not a plugin), off by default; toggled by `devflow compliance --enable/--disable/--set <ids>`, installed by `src/targets/claude-code/compliance-install.ts` and composed from per-framework fragments by `src/core/compliance-compose.ts`. Every install carries the skill and all six framework references; the machine switch owns the rule (installed and stamped when on), the SKILL.md stamp (the machine's frameworks, or a neutral stamp when off) and which build of the workflow prompts installs (the paragraphs below). The review lens runs from the settings line's `COMPLIANCE` — the union of the machine's ids and the `project.json` `compliance` ids of the default branch (its local tracking copy) and the worktree, so a branch adds frameworks and never removes one and an unreadable file never lowers the lens (D-LENS-UNION); `off` only when no layer declares compliance, `generic` when one does with no valid ids — and an agent loads `references/{id}.md` only for the ids its spawn prompt's compliance directive names. The lens is not a machine switch, so no install-time variant can carry it (the posting build below follows the machine switch alone and never decides the lens): the command adds that directive to a Code, Fix, Review or Design spawn prompt only when the lens is on, no agent body names the compliance skill, and a lens-off spawn carries nothing about compliance (D-COMPLIANCE-INJECT). Enabled at any framework count, zero included, it makes `required` the evidence-policy floor on that machine, and any repository `compliance` key, empty or malformed included, raises it too; the lens never decides evidence.

**Compliance-off build**: the machine switch alone picks the posting variant of the prompts, and a repository `compliance` key cannot restore a posting step: it keeps the lens on, locally, and nothing posts. The build splits each compiled prompt on two axes, curation and compliance (`<!-- compliance:on -->`, `<!-- compliance:off -->`, `<!-- compliance:end -->`; the tree layout is in `docs/reference/file-organization.md`). With compliance off the installer takes the compliance-off file of each host that carries an arm (the `/implement`, `/resolve`, `/code-review`, `/bug-analysis`, `/dynamic-build`, `/dynamic-tickets`, `/plan` and `/release` commands, and the Git and Triage agents) and refuses an install that has no file for the machine's exact axes. An off prompt holds no step that posts test-plan evidence, review or resolution summaries, backlog entries, review-thread replies, wave reports, plan artifacts or release back-links to GitHub or a tracker. It keeps the plain writes: the pull request with its issue link, the issue that `/plan` asks for, and the tickets `/dynamic-tickets` files. Where the repository requires evidence, each off command prints the fixed line `TRACEABILITY: DEGRADED (compliance off on this machine; the repository requires evidence)` once. The install omits the posting references as well. A reference module under `src/assets/mds/` can carry compliance arms. The build splits each module per operation section, then per arm, and writes the compliance-off references as a complete tree, `dist/compliance-off/skills/git/references/`, that equals `installedReferenceManifest({ compliance: false })`. The compliance-on tree does not change. That manifest omits 16 operation files: the four `pr/` files and the four tracker files of each of the three providers, for the eight operations in `POSTING_OPS` (`src/core/mds-variants.ts`). It omits the publication-gate document too. The check-merge-readiness operation stays. Three flat files sit outside the pruned `pr/` and `tracker/` subtrees: `publication-gate.md`, `github-posting.md` (the static GitHub posting recipes) and `implement-evidence-asks.md` (read only by the compliance-on arms of `/implement`). One list, `COMPLIANCE_OFF_REMOVED_SKILL_FILES` in `src/core/compliance-off-files.ts`, names them. A compliance-off install removes each by exact name and unlinks a link at that path without following it. Turning compliance on restores each file byte for byte. The install has one off source root: when the compliance-off tree is absent, it refuses and never falls back to the compliance-on references.

**Variant converge**: one composed converge, `convergeVariantAxes` in `src/targets/claude-code/curation-install.ts`, serves `devflow init`, `devflow curation` and `devflow compliance` (enable, disable, `--set` and the interactive enable). It composes the per-kind converges, each of which returns a result and never throws, and a toggle ends byte-equal, apart from stamps, to a fresh install with the same two switches. The references are one of those kinds: the converge overlays the `devflow:git` references from the one source root of the compliance switch, then runs the removal list with compliance off or the restore with compliance on. With compliance off, an absent off tree is a failure that writes nothing, and the converge never falls back to the compliance-on references. A compliance-off converge that cannot show the installed prompts and references free of posting steps fails closed: `devflow compliance --disable` records the switch as off, lists the installed files that still post and exits 1, and on a version skew or with no manifest it exits 1 and says that posting steps remain installed until `devflow init`. A curation-only failure stays a warning. After a clean converge the manifest records `installedVariants: {curation, compliance}`; an absent or malformed record reads as unknown and nothing heals it. `devflow compliance --status` shows the record as `Posting: installed | not installed | mismatch (run devflow init) | unknown (run devflow init)`. `devflow init` prints the posting notice once, when the record moves from posting (compliance on, or no record) to non-posting, and prints nothing on the next run or while compliance is on.

**Local results (compliance off)**: an off build keeps each result in a local file under the checkout's `.devflow/docs/` and marks it `(local; not posted)`. A git-tracked evidence file counts as absent, like a tracked `config.json`: `verify-evidence.cjs` does not read one, and it does not write over a tracked result file. `/code-review` writes `reviews/{branch-slug}/{timestamp}/review-summary.md`, and its reviewed head goes to `{git-dir}/devflow/reviews/{branch-slug}/.last-review-head`. `/resolve` writes `resolution-summary.md` in the same directory, appends its claims to `evidence-{branch_slug}.md`, and writes `evidence-result-{branch_slug}.md` and `readiness-{branch_slug}.md`. `/implement` writes `evidence-{branch_slug}.md` and `evidence-result-{branch_slug}.md`. `/dynamic-build` writes `waves/{slug}/{ts}/wave-report.md`, `evidence-wave-{slug}.md`, `evidence-result-wave-{slug}.md` and, in step 7, `readiness-wave-{slug}.md`. `/bug-analysis` posts nothing, writes `bug-analysis/{branch-slug}/{timestamp}/bug-analysis-summary.md`, and keeps its analysed head in `{git-dir}/devflow/bug-analysis/{branch-slug}/.last-analysis-head`, `/plan` writes its design artifact and `/release` writes nothing new. The evidence-result and readiness files come from `verify-evidence.cjs verify --comment-out` and `readiness --out`, which make no remote write; the wave block of `/dynamic-build` lists links only (`Refs` lines for a `#N` or `KEY-N` reference, never `Closes`).

**Publish guard (compliance off)**: `verify-evidence.cjs publish` reads the compliance switch from the machine manifest, `~/.devflow/manifest.json` (`features.compliance.enabled`), before it makes a work directory or any gh call. It ignores the devflow directory override in the environment and reads no repository file, so no checkout can switch it on. When the switch is not `true`, it prints `TRACEABILITY: DEGRADED (compliance off)`. When the manifest is missing, unreadable or malformed, or `features.compliance` has another shape, it prints `TRACEABILITY: DEGRADED (compliance state unreadable)`. Either way it exits 2 and writes nothing. A manifest with no `features.compliance` key reads as off. The guard returns its outcome and never throws, because the catch in `main` would turn a throw into `evidence unavailable` and hide the reason. The stdout gate in `settleOutcome` admits each of the two lines only with exit code 2. With compliance on, `publish` behaves as before.

**Claude Code Flags**: the typed registry and its rules live in `src/core/flags.ts` (registry + JSDoc); manage with `devflow flags`. `--enable`/`--disable` are boolean-only — non-boolean flags use `--set`. Enabling `suppress-attribution` overwrites any existing `attribution` value; disable only deletes the exact devflow shape, never a user's custom attribution. `subagent-cache-5m` writes `subagentPromptCacheTtl: "5m"` and guards a scalar: disable and uninstall delete the key only while it holds `"5m"`, and init and the flags TUI adopt it off over a user's own value (D-ADOPT-RESPECTS-USER); `init --reset` applies the default. Narrow boolean flags with `isEnvBooleanFlag` — a `target.type` check does not narrow `onPayload`. The literal 'unset' is never a displayed value.

**Model Strategy**: an explicit `model:` in agent frontmatter overrides the user's session model. The Tracker agent's tier is a constant with no tuning config: the hook's `TRACKER_MODEL` literal is `case`-allowlisted and pinned equal to `loadShippedAgentDefaults()['tracker'].model`. The memory worker's model and effort come from the `WORKER_AGENTS.memory` entry: the hook's fallback literals are pinned equal to that row by test, and a `devflow agents` override of `memory` is read at run time and wins. Users override per agent via `devflow agents`; overrides persist in `~/.devflow/agent-models.json` and are re-applied on every `devflow init`.

**Review publication**: PR-comment publication is visibility-gated (D10, fail-closed to a counts-only stub on public/unknown repos; `reviewPublication: auto|full|off` in `.devflow/config.json`; the team's `project.json` value only caps it, never raises it, so a branch cannot lift publication above `auto`). Under a `required` evidence policy a resolved `off` becomes `stub`, so a counts-only record still reaches the PR; `stub` is never a config value. The test-plan evidence comment makes no visibility probe: it is a STUB under `auto` as well, FULL only under `full`, and not posted under `off`. Every posted body passes the deterministic secret scrubber (D11, unconditional; a missing or failing scrubber emits `TRACEABILITY: DEGRADED (redaction unavailable)` and suppresses the post rather than publishing unredacted content). File sinks chain the scrubber with `&&`, so a non-zero exit means the write does not happen. Tool-call sinks use `redact-secrets.cjs --emit`, which frames the result as `D11-OK <nonce> <sha256> <bytes> <n> [type:count,…]` with a per-invocation 32-hex nonce (an unframed `D11-OK` literal is forgeable by anyone who can write an issue comment), prints `D11-FAIL <reason>` with an **empty body** on every non-zero path, and requires the consumer to verify the received body's byte length against `<bytes>` before posting [DR-06]. Review-cycle convergence warnings never block the pipeline.

**Private sections**: both summary operations (review and resolution) leave out each section whose heading starts with the word `Private` before either mode. When no public text remains, they post nothing and report `DEGRADED (no postable summary)`.

**Evidence policy**: `resolve-evidence-policy.cjs` resolves `EVIDENCE_POLICY` (`required` | `standard`) once per run from the `evidence` key of `.devflow/project.json` as committed on the default branch — the only authority. Offline it names that branch from the local `origin/HEAD` and folds its tracking copy (D-OFFLINE-ORIGIN-HEAD); only with no `origin/HEAD` does the worktree's file govern, flagged `remote-unavailable`. HEAD feeds only the `pr-changes-policy` warning. Where a source's `project.json` has no `evidence`, a `.devflow/policy.json` there is never parsed: its presence alone resolves `required` with `invalid-file` (D-POLICY-JSON-RETIRED). It writes nothing, every failure resolves `required`, and local sources (enabled compliance, the worktree's file) only raise it. A `compliance` key in `project.json` on the default branch, the tracking branch or the worktree — never HEAD — raises the floor to `required`, whatever its value. Operations never see the policy, only `ISSUE_REQUIRED`, `APPLY_CONVENTIONS` and `REQUIRE_NON_AUTHOR_APPROVAL`, mapped in the resolver alone, so no prompt restates the mapping. Test-plan states are assigned only by `pr-evidence.cjs` (the pure core: grammars, markers, the state ladder) and `verify-evidence.cjs` (its I/O half), never by a prompt; `release-trace.cjs` computes the git-only release trace map. `/code-review` and `/bug-analysis` carry no ticket gate.

**Tracker**: Built-in issue-tracker provider selection (not a plugin) over `github | jira | linear`. The machine default is chosen at `devflow init` (wizard, or `--tracker <id>`) and stored in `manifest.features.tracker.provider`, default `github`; a repository selects its own in `.devflow/project.json` (`tracker` provider, site, key), trusted automatically. Every install carries every provider: all generated references on the `devflow:git` skill, the tool-call contract `references/tracker/_mcp.md` and the Tracker agent file. Section 3 of `session-start-context` always installs and gates at runtime. Skills are scoped by selection: each plugin declares the skills it uses but does not own in a `requires:` list, a bidirectional closure guard holds that list against commands, agents and skill bodies, and the Review agent's focus-templated skill reference is the one classified exception.

**Tracker operations**: a Git spawn that runs a tracker operation reads `references/tracker/_contract.md` once, runs `resolve-settings.cjs` as it directs and takes provider, site and key from the settings line — the repository's choice, else the machine default, else `github`; a personal `config.json` override can only narrow it. Under a non-`github` provider it also reads `references/tracker/_mcp.md` once, the tool-call contract. A spawn that runs only a PR-host operation reads neither. Servers are scoped per capability: the unique qualifying server wins, two or more is a degraded run with no call. A reference renders by the resolved provider's own documented default; release evidence is gathered in the provider's own reference grammar with project-key equality, never a bare number. A refusal reports `TRACEABILITY: DEGRADED (<reason>)`, and each actionable reason implies its remedy: `tracker not configured` — select a provider; `tracker configuration mismatch (repository override)` or `(conventions file)` — another source names another provider, so re-select or drop it; `tracker.md required fields incomplete` — edit the conventions file in `~/.devflow/tracker/`; `no tracker tool for {capability}` — connect a server offering it, or add it with `tracker --servers`; `redaction unavailable` — the scrubber could not run, so nothing posts. On Linear `dedup unavailable — duplicate possible` is permanent: the workspace cannot tell devflow which account it is, so a back-link posts with that warning rather than being withheld.

**Tracker lifecycle**: `devflow init --tracker <id>` selects non-interactively. `devflow tracker --set <id>` sets only the machine default: manifest, attempt counters, sentinel; `--servers <names|default>` sets the servers stamped onto the Git and Tracker agents. `devflow tracker --status` reports the machine provider, an `Effective:` line when a repository selects one, whether conventions have been learned, a `Mechanics:` line counting the installed reference files, and a `Servers:` line. When a session's provider is not `github` a background Tracker agent runs once, takes an observable claim (`CLAIMED`, or `LOST` and an immediate exit if another run holds it), and writes `~/.devflow/tracker/{provider}.md` exactly once or not at all, scrub-gated fail-closed, with `# UNRESOLVED:` lines for what it could not establish. Each provider's conventions are learned from the first repository that uses it. Those files are yours: hand-editable, kept on uninstall.
